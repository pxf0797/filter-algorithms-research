# 回测数据分析示例

> 基于修正后的数据存储 scope，展示典型分析场景的代码示意。每个示例包含场景描述、可运行的伪代码/SQL、预期输出形式。
> 存储范围：仅信号到交易链路数据，不含 K 线/滤波等原始数据。多周期独立存储，不做 ffill 合并。
> 目标：帮助读者判断"只存信号→交易链路"的方案是否满足分析需求，以及需要调整什么。

## 2. 数据加载示例

### 2.1 单 Session 单周期加载

场景：加载某一个 ticker 某次回测的指定周期信号数据、交易明细和 BS 标记。

```python
import polars as pl

# 加载日线信号
sig_d1 = pl.read_parquet("data/AAPL/sess_20240701_001/signals/d1.parquet")
print(sig_d1.columns)
# → ['bar_index', 'timestamp', 'sig', 'eps', 'sigma_v', 'v', 'a',
#    'mu_v', 'dur', 'pair_count', 'pnl_long', 'pnl_short',
#    'long_mask', 'short_mask']

# 加载交易明细
trades = pl.read_parquet("data/AAPL/sess_20240701_001/trades.parquet")
print(trades.columns)
# → ['trade_id', 'view', 'type', 'entry_bar', 'exit_bar',
#    'entry_price', 'exit_price', 'return_pct', 'exit_reason']

# 加载 BS 买卖标记
bs = pl.read_parquet("data/AAPL/sess_20240701_001/bs_markers.parquet")
print(bs.columns)
# → ['view', 'type', 'label', 'bar_idx', 'date', 'exit_reason']
```

要点：三个文件各自独立，通过 `bar_index`/`bar_idx` 和 `view` 关联。信号文件按周期拆分（如 `d1.parquet`、`h1.parquet`），不合并到一个宽表中。

### 2.2 多周期信号同时加载

场景：同一个 session 跑了日线和 60 分钟线，需要同时加载两个周期的信号。

```python
import polars as pl
from pathlib import Path

session_dir = Path("data/AAPL/sess_20240701_001/signals")
signals = {}
for f in session_dir.glob("*.parquet"):
    tf = f.stem  # 如 "d1", "h1"
    signals[tf] = pl.read_parquet(f)

print(f"加载周期: {list(signals.keys())}")
# → 加载周期: ['d1', 'h1']
print(f"d1 行数: {signals['d1'].height}, h1 行数: {signals['h1'].height}")
# → d1 行数: 250, h1 行数: 1500
```

要点：不同周期的 bar 数量天然不同（日线约 250 根/年，60 分钟约 1500 根/年），各自独立文件无需对齐。

### 2.3 跨 Session 聚合

场景：汇总某个 ticker 在所有 session 中的交易表现，无需手动拼接文件。

```sql
-- DuckDB glob 直接读取目录下所有 trades.parquet
SELECT
    regexp_extract(filename, '/(sess_[^/]+)/', 1) AS session_id,
    count(*)                              AS trade_count,
    avg(return_pct)                       AS avg_return,
    sum(CASE WHEN return_pct > 0 THEN 1 ELSE 0 END) * 1.0 / count(*) AS win_rate,
    sum(return_pct)                       AS total_return
FROM read_parquet('data/AAPL/*/trades.parquet', filename=true)
GROUP BY session_id
ORDER BY total_return DESC;
```

预期输出：每个 session 一行汇总，立即看出哪些 session 盈利、胜率是否异常。

### 2.4 按时间范围过滤

场景：只加载 2024 年 Q1 的信号数据，利用 Parquet 谓词下推减少 IO。

```python
from datetime import datetime

# Polars 下推 timestamp 过滤到 Parquet 层，只读相关 row group
df = pl.scan_parquet("data/AAPL/*/signals/d1.parquet").filter(

    )

```

## 3. 信号分析

> 新增章节：基于 signals/{tf}.parquet 的 schmitt 信号状态进行统计分析。

### 3.1 信号翻转频率

场景：统计信号的翻转频率（sig 符号变化次数），评估策略的交易频率是否合理。

```sql
-- 计算日线信号的翻转次数
WITH signal_changes AS (
    SELECT
        bar_index,
        timestamp,
        sig,
        LAG(sig) OVER (ORDER BY bar_index) AS prev_sig,
        CASE WHEN sig * LAG(sig) OVER (ORDER BY bar_index) < 0 THEN 1 ELSE 0 END AS flipped
    FROM read_parquet('data/AAPL/sess_20240701_001/signals/d1.parquet')
)
SELECT
    count(*)                          AS total_bars,
    sum(flipped)                      AS flip_count,
    sum(flipped) * 1.0 / count(*)     AS flip_rate,
    -- 平均每 N 根 bar 翻转一次
    count(*) * 1.0 / nullif(sum(flipped), 0) AS bars_per_flip
FROM signal_changes;
```

预期输出：日线约 250 根 bar 中翻转 8-15 次，翻转率 3%-6%。

### 3.2 信号持续期分布

场景：分析每次信号（连续同号）的持续 bar 数分布，识别是否存在频繁抖动。

```sql
-- 计算信号持续期
WITH sig_groups AS (
    SELECT
        bar_index,
        sig,
        -- 当 sig 符号变化时开始新分组
        SUM(CASE WHEN sig * LAG(sig) OVER (ORDER BY bar_index) < 0
                 OR LAG(sig) OVER (ORDER BY bar_index) IS NULL
            THEN 1 ELSE 0 END) OVER (ORDER BY bar_index) AS run_id
    FROM read_parquet('data/AAPL/sess_20240701_001/signals/d1.parquet')
    WHERE sig != 0
),
run_lengths AS (
    SELECT run_id, count(*) AS duration, MAX(sig) AS direction
    FROM sig_groups
    GROUP BY run_id
)
SELECT
    CASE WHEN direction > 0 THEN 'long' ELSE 'short' END AS signal_type,
    count(*)                                              AS run_count,
    avg(duration)                                         AS avg_duration,
    median(duration)                                      AS median_duration,
    min(duration)                                         AS min_duration,
    max(duration)                                         AS max_duration,
    -- 短持续期占比（≤3 bar 视为抖动）
    sum(CASE WHEN duration <= 3 THEN 1 ELSE 0 END) * 1.0 / count(*) AS short_run_ratio
FROM run_lengths
GROUP BY signal_type
ORDER BY signal_type;
```

预期输出：区分多空方向的持续期分布，短持续期占比过高（>30%）说明信号抖动严重。

### 3.3 多空比例

场景：统计信号在多空方向上的时间占比，检查策略是否存在方向偏差。

```sql
SELECT
    sum(CASE WHEN sig > 0 THEN 1 ELSE 0 END) * 1.0 / count(*) AS long_ratio,
    sum(CASE WHEN sig < 0 THEN 1 ELSE 0 END) * 1.0 / count(*) AS short_ratio,
    sum(CASE WHEN sig = 0 THEN 1 ELSE 0 END) * 1.0 / count(*) AS neutral_ratio,
    -- 实际持仓比例（mask 为 True 的 bar）
    sum(CASE WHEN long_mask THEN 1 ELSE 0 END) * 1.0 / count(*)  AS long_holding_ratio,
    sum(CASE WHEN short_mask THEN 1 ELSE 0 END) * 1.0 / count(*) AS short_holding_ratio
FROM read_parquet('data/AAPL/sess_20240701_001/signals/d1.parquet');
```

预期输出：多空信号比例约 50:50 为理想状态；若偏差超过 70:30，策略可能有方向偏好。

### 3.4 信号强度分布

场景：分析 sig 值的分布特征（均值、标准差、极端值），评估信号质量。

```python
import polars as pl

df = pl.read_parquet("data/AAPL/sess_20240701_001/signals/d1.parquet")

# 信号强度统计
stats = df.select([
    pl.col("sig").mean().alias("mean_sig"),
    pl.col("sig").std().alias("std_sig"),
    pl.col("sig").abs().max().alias("max_abs_sig"),
    pl.col("sig").abs().quantile(0.5).alias("median_abs_sig"),
    pl.col("sig").abs().quantile(0.9).alias("p90_abs_sig"),
    pl.col("sig").abs().quantile(0.99).alias("p99_abs_sig"),
])
print(stats)
```

预期输出：sig 范围通常 [-1, 1]，极端值出现在趋势强烈的时段。配合 sigma_v 列可分析信号波动率。

## 4. 交易分析

### 4.1 交易统计

场景：快速计算胜率、盈亏比等核心指标（适配新的 trades.parquet schema）。

```sql
SELECT
    count(*)                                                          AS trade_count,
    sum(CASE WHEN return_pct > 0 THEN 1 ELSE 0 END) * 1.0 / count(*) AS win_rate,
    avg(CASE WHEN return_pct > 0 THEN return_pct END)                 AS avg_win,
    avg(CASE WHEN return_pct < 0 THEN return_pct END)                 AS avg_loss,
    abs(avg_win / nullif(avg_loss, 0))                                AS profit_factor,
    sum(return_pct)                                                   AS total_return,
    avg(return_pct)                                                   AS avg_return
FROM read_parquet('data/AAPL/*/trades.parquet');
```

要点：新 schema 使用 `return_pct` 替代旧 `pnl_pct`，使用 `type`（long/short）替代旧 `side`，使用 `exit_reason` 替代旧 `exit_reason`（同名但值域可能不同）。

### 4.2 逐笔交易审查

场景：找出亏损最大的 10 笔交易，检查入场/出场时机和退出原因。

```sql
SELECT
    trade_id, view, type,
    entry_bar, exit_bar,
    entry_price, exit_price,
    return_pct, exit_reason,
    (exit_bar - entry_bar) AS hold_bars
FROM read_parquet('data/AAPL/*/trades.parquet')
ORDER BY return_pct ASC
LIMIT 10;
```

预期输出：每笔亏损交易的入场原因、持仓时长、亏损幅度、退出原因（止损/信号翻转/到期），便于定位策略缺陷。

### 4.3 按退出原因分组统计

场景：分析不同退出原因（止损/止盈/信号翻转等）的盈亏分布。

```sql
SELECT
    exit_reason,
    count(*)                                                          AS trade_count,
    sum(CASE WHEN return_pct > 0 THEN 1 ELSE 0 END) * 1.0 / count(*) AS win_rate,
    avg(return_pct)                                                   AS avg_return,
    sum(return_pct)                                                   AS total_return
FROM read_parquet('data/AAPL/*/trades.parquet')
GROUP BY exit_reason
ORDER BY total_return DESC;
```

预期输出：对比止损退出 vs 信号翻转退出的盈亏差异，帮助判断哪个退出条件更优。

### 4.4 按时间段分组统计

场景：按月份查看策略表现是否稳定。

```sql
-- 通过 entry_bar 关联 signals 获取 timestamp
WITH trade_dates AS (
    SELECT
        t.*,
        s.timestamp AS entry_time
    FROM read_parquet('data/AAPL/*/trades.parquet') t
    JOIN read_parquet('data/AAPL/*/signals/d1.parquet') s
      ON t.entry_bar = s.bar_index
)
SELECT
    strftime(entry_time, '%Y-%m')          AS month,
    count(*)                               AS trades,
    sum(return_pct)                        AS monthly_return,
    sum(CASE WHEN return_pct > 0 THEN 1 ELSE 0 END) * 1.0 / count(*) AS win_rate
FROM trade_dates
GROUP BY month
ORDER BY month;
```

要点：trades.parquet 不直接存时间戳，需要通过 `entry_bar` 关联 signals 获取。这是"不存 K 线"方案的代价——分析时多一次 join。

## 5. 跨周期对比

> 多周期数据独立存储，不合并到宽表，不做 ffill。跨周期分析需注意 bar 不对齐问题。

### 5.1 信号一致性分析

场景：检查日线和 60 分钟线在同一时段是否存在矛盾信号（一个做多一个做空）。

```python
import polars as pl

d1  = pl.read_parquet("data/AAPL/sess_20240701_001/signals/d1.parquet")
h1  = pl.read_parquet("data/AAPL/sess_20240701_001/signals/h1.parquet")

# 关键：不同周期 bar 不对齐，不能用 bar_index 直接 join
# 需要使用 asof join（按时间就近匹配）
d1_ts = d1.select(["timestamp", pl.col("sig").alias("sig_d1")])
h1_ts = h1.select(["timestamp", pl.col("sig").alias("sig_h1")])

# 将 h1 的 timestamp 就近匹配到 d1 的 timestamp
merged = h1_ts.join_asof(
    d1_ts.sort("timestamp"),
    on="timestamp",
    strategy="nearest"
)

# 找出矛盾信号（同时有信号且方向相反）
conflicts = merged.filter(
    (pl.col("sig_d1") != 0) &
    (pl.col("sig_h1") != 0) &
    (pl.col("sig_d1") * pl.col("sig_h1") < 0)
)

print(f"信号矛盾次数: {conflicts.height}")
print(conflicts.head(10))
```

要点：跨周期 bar 数不同（日线 250 根 vs 60 分钟线 1500 根），`bar_index` 无对齐语义，必须通过 timestamp 做 asof join。`strategy="nearest"` 将细周期匹配到最近的粗周期时间点。

### 5.2 粗周期信号在细周期上的实际表现

场景：日线发出做多信号后，60 分钟线的实际 PnL 走势。

```sql
-- 先按日期聚合：日线信号日 → 当天所有 60 分钟 bar 的表现
WITH daily_sig AS (
    SELECT
        date_trunc('day', timestamp) AS trade_date,
        sig                          AS d1_sig,
        long_mask                    AS d1_long,
        short_mask                   AS d1_short
    FROM read_parquet('data/AAPL/sess_20240701_001/signals/d1.parquet')
    WHERE sig != 0
),
hourly_perf AS (
    SELECT
        date_trunc('day', timestamp) AS trade_date,
        pnl_long,
        pnl_short
    FROM read_parquet('data/AAPL/sess_20240701_001/signals/h1.parquet')
)
SELECT
    d.trade_date,
    d.d1_sig,
    sum(h.pnl_long)  AS intraday_pnl,
    count(*)         AS h1_bar_count
FROM daily_sig d
JOIN hourly_perf h ON d.trade_date = h.trade_date
GROUP BY d.trade_date, d.d1_sig
ORDER BY d.trade_date;
```

要点：通过 `date_trunc('day', timestamp)` 对齐粗/细周期的日期，按天聚合细周期数据。若需更精确的 bar 级对齐，使用 asof join。

### 5.3 多周期持仓状态对比

场景：同一时刻，日线持仓掩码 vs 60 分钟持仓掩码是否一致。

```python
# 使用 asof join 将两个周期的 long_mask 对齐到统一时间轴
d1_masks = d1.select([
    "timestamp",
    pl.col("long_mask").alias("long_d1"),
    pl.col("short_mask").alias("short_d1"),
])
h1_masks = h1.select([
    "timestamp",
    pl.col("long_mask").alias("long_h1"),
    pl.col("short_mask").alias("short_h1"),
])

merged = h1_masks.join_asof(
    d1_masks.sort("timestamp"),
    on="timestamp",
    strategy="nearest"
)

# 持仓状态不一致的 bar
mismatch = merged.filter(
    (pl.col("long_d1") != pl.col("long_h1")) |
    (pl.col("short_d1") != pl.col("short_h1"))
)
print(f"持仓不一致的 bar 数: {mismatch.height} / {merged.height}")
```

## 6. BS 标记时序分析

> 新增章节：基于 bs_markers.parquet 分析 BS 标记与信号的时序关系。

### 6.1 BS 标记与信号对照

场景：检查 BS 标记的时间点是否与信号翻转点一致，分析延迟。

```python
import polars as pl

bs   = pl.read_parquet("data/AAPL/sess_20240701_001/bs_markers.parquet")
d1   = pl.read_parquet("data/AAPL/sess_20240701_001/signals/d1.parquet")

# 按 bar_idx 关联 BS 标记和信号
bs_with_sig = bs.join(
    d1.select(["bar_index", "sig", "timestamp"]),
    left_on="bar_idx",
    right_on="bar_index",
    how="left"
)

# 按 BS 类型分组统计
print(bs_with_sig.group_by("type").agg([
    pl.count(),
    pl.col("sig").mean().alias("avg_sig_at_marker"),
    pl.col("label").value_counts().alias("label_dist"),
]))
```

预期输出：按 view 和 type 分组，展示每个 BS 标记点对应的信号值分布。

### 6.2 BS 标记延迟分析

场景：信号翻转后，BS 标记多久才出现？分析信号→标记的延迟分布。

```python
# 识别信号翻转点
d1_flips = d1.with_columns(
    pl.when(
        pl.col("sig") * pl.col("sig").shift(1) < 0
    ).then(pl.lit(1)).otherwise(pl.lit(0)).alias("is_flip")
).filter(pl.col("is_flip") == 1)

# 对每个 BS 标记，找到最近的信号翻转点
bs_with_nearest_flip = bs.join_asof(
    d1_flips.select(["bar_index", "timestamp"]).with_columns(
        pl.col("timestamp").alias("flip_time"),
        pl.col("bar_index").alias("flip_bar"),
    ).sort("bar_index"),
    left_on="bar_idx",
    right_on="bar_index",
    strategy="nearest"
)

# 计算延迟（bar 数）
delay = bs_with_nearest_flip.with_columns(
    (pl.col("bar_idx") - pl.col("flip_bar")).alias("delay_bars")
)

print("BS 标记延迟分布（bar 数）:")
print(delay.select("delay_bars").describe())
```

预期输出：延迟中位数应在 0-2 bar 以内。延迟过大说明 BS 标记逻辑与信号翻转逻辑存在偏差。

### 6.3 按退出原因分析 BS 标记

场景：BS 标记的 `exit_reason` 字段记录了标记触发原因，分析各原因的分布。

```sql
SELECT
    exit_reason,
    label,
    count(*)                              AS count,
    count(*) * 1.0 / sum(count(*) ) OVER() AS ratio
FROM read_parquet('data/AAPL/*/bs_markers.parquet')
GROUP BY exit_reason, label
ORDER BY count DESC;
```

预期输出：展示各退出原因（signal_flip/stop_loss/take_profit 等）对应的买卖标记数量和占比。

### 6.4 BS 事件流回放

场景：从 events.jsonl 读取 BS 变更事件，还原标记变更时序。

```python
import json

events = []
with open("data/AAPL/sess_20240701_001/events.jsonl") as f:
    for line in f:
        evt = json.loads(line)
        if evt.get("event_type") == "bs_change":
            events.append(evt)

# 按时间排序
events.sort(key=lambda e: (e["view_index"], e["bar_index"]))

# 统计每个 view 的 BS 变更次数
from collections import Counter
view_counts = Counter(e["view_index"] for e in events)
print(f"各 view BS 变更次数: {dict(view_counts)}")
```

要点：events.jsonl 提供 BS 标记变更的完整事件流，可用于还原任何时间点的 BS 状态，无需重新计算。

## 7. 信号→交易对照

> 新增章节：从信号翻转点到 trade_records 的对应关系分析。

### 7.1 信号翻转触发交易检查

场景：验证每次信号翻转是否都正确触发了对应的交易。

```python
import polars as pl

d1     = pl.read_parquet("data/AAPL/sess_20240701_001/signals/d1.parquet")
trades = pl.read_parquet("data/AAPL/sess_20240701_001/trades.parquet")

# 找出信号翻转点
flips = d1.with_columns(
    pl.when(
        pl.col("sig") * pl.col("sig").shift(1) < 0
    ).then(pl.lit(1)).otherwise(pl.lit(0)).alias("is_flip")
).filter(pl.col("is_flip") == 1).select([
    "bar_index", "timestamp", "sig",
    pl.col("sig").shift(1).alias("prev_sig")
])

# 找出每个翻转点附近是否有对应的交易
for flip_row in flips.iter_rows(named=True):
    nearby_trades = trades.filter(
        (pl.col("entry_bar") >= flip_row["bar_index"] - 2) &
        (pl.col("entry_bar") <= flip_row["bar_index"] + 2)
    )
    if nearby_trades.height == 0:
        print(f"⚠️ bar {flip_row['bar_index']} ({flip_row['timestamp']}) "
              f"信号翻转但无对应交易: {flip_row['prev_sig']:.2f} → {flip_row['sig']:.2f}")
```

预期输出：列出信号翻转但未触发交易的异常点，以及附近 2 bar 内有交易的正常匹配。

### 7.2 交易持仓期信号分析

场景：每笔交易持仓期间，信号状态是否稳定。

```sql
-- 对每笔交易，统计持仓期间的信号稳定性
WITH trade_signals AS (
    SELECT
        t.trade_id,
        t.type,
        t.entry_bar,
        t.exit_bar,
        t.return_pct,
        s.bar_index,
        s.sig
    FROM read_parquet('data/AAPL/*/trades.parquet') t
    JOIN read_parquet('data/AAPL/*/signals/d1.parquet') s
      ON s.bar_index BETWEEN t.entry_bar AND t.exit_bar
)
SELECT
    trade_id,
    type,
    return_pct,
    count(*)                                    AS bars_held,
    -- 信号与交易方向一致的 bar 占比
    sum(CASE WHEN (type = 'long' AND sig > 0)
              OR (type = 'short' AND sig < 0)
        THEN 1 ELSE 0 END) * 1.0 / count(*)     AS signal_alignment,
    -- 信号标准差（越小越稳定）
    stddev(sig)                                 AS signal_volatility
FROM trade_signals
GROUP BY trade_id, type, return_pct
ORDER BY signal_alignment ASC
LIMIT 20;
```

预期输出：signal_alignment 接近 1.0 说明持仓期间信号稳定；低于 0.5 说明信号在持仓期间多次翻转，策略可能需要优化。

## 8. 批量回测对比

### 8.1 跨 Session 交易汇总

```sql
-- 汇总所有 session 的交易表现
SELECT
    regexp_extract(filename, '/([^/]+)/[^/]+/trades\.parquet$', 1) AS ticker,
    regexp_extract(filename, '/(sess_[^/]+)/', 1)                   AS session_id,
    count(*)                                                         AS trade_count,
    sum(return_pct)                                                  AS total_return,
    avg(return_pct)                                                  AS avg_return,
    stddev(return_pct)                                               AS return_volatility,
    sum(return_pct) / nullif(stddev(return_pct), 0)                  AS sharpe_approx
FROM read_parquet('data/*/*/trades.parquet', filename=true)
GROUP BY ticker, session_id
ORDER BY sharpe_approx DESC;
```

## 9. 数据质量检查

### 9.1 bar_index 连续性校验

```sql
-- 检测每个信号文件的 bar_index 是否连续
SELECT
    filename,
    count(*)                             AS bar_count,
    max(bar_index) - min(bar_index) + 1  AS expected_count,
    expected_count - bar_count           AS missing_bars
FROM read_parquet('data/AAPL/*/signals/*.parquet', filename=true)
GROUP BY filename
HAVING missing_bars > 0;
```

### 9.2 信号文件完整性检查

场景：确保每个 session 的每个周期都有对应的 signals 文件。

```python
from pathlib import Path

# 检查每个 session 目录是否包含预期的信号文件
expected_tfs = {"d1", "h4", "h1"}  # 根据回测预设调整

for session_dir in Path("data/AAPL/").glob("sess_*"):
    signal_dir = session_dir / "signals"
    if not signal_dir.exists():
        print(f"⚠️ {session_dir.name}: 缺少 signals/ 目录")
        continue
    actual_tfs = {f.stem for f in signal_dir.glob("*.parquet")}
    missing = expected_tfs - actual_tfs
    if missing:
        print(f"⚠️ {session_dir.name}: 缺少周期 {missing}")

# 同时检查 trades.parquet 和 bs_markers.parquet 是否存在
for session_dir in Path("data/AAPL/").glob("sess_*"):
    for required in ["trades.parquet", "bs_markers.parquet"]:
        if not (session_dir / required).exists():
            print(f"⚠️ {session_dir.name}: 缺少 {required}")
```

### 9.3 BS 标记与交易的一致性校验

场景：检查 BS 标记的买卖点是否有对应的交易记录。

```sql
-- 检查买入标记是否有对应的 long 交易
SELECT
    bs.bar_idx, bs.label, bs.type,
    t.trade_id, t.entry_bar
FROM read_parquet('data/AAPL/*/bs_markers.parquet') bs
LEFT JOIN read_parquet('data/AAPL/*/trades.parquet') t
  ON bs.bar_idx BETWEEN t.entry_bar - 1 AND t.entry_bar + 1
 AND bs.type = t.type
WHERE t.trade_id IS NULL
  AND bs.label != 0;
```

预期输出：列出有 BS 标记但没有对应交易的异常点。正常情况下买入标记附近应有 long 交易，卖出标记附近应有 short 交易。

### 9.4 跨文件记录数一致性

```sql
-- 确保 trades 中的 view 都在 signals 中有对应数据
SELECT DISTINCT t.view
FROM read_parquet('data/AAPL/*/trades.parquet') t
WHERE t.view NOT IN (
    SELECT DISTINCT view
    FROM read_parquet('data/AAPL/*/signals/d1.parquet')
```

## 10. 待讨论

以下设计选择需要确认，直接影响存储方案和分析效率：

- [ ] **trades.parquet 合并还是按周期拆分**：当前所有周期的交易合并到一个 `trades.parquet`，通过 `view` 字段区分。是否应该每个周期独立存 `trades_{tf}.parquet`？合并方案跨周期查询方便但单文件变大；拆分方案与 signals 目录结构一致但跨周期分析需 union。
- [ ] **CSV 输出策略**：CSV 文件是否自动生成（每次回测都输出）还是作为可选参数（`--csv` flag）？自动生成方便人工快速查看但增加 IO 和磁盘占用；可选策略更精简但需要手动开关。
- [ ] **signals 文件的 view 字段**：当前 signals/{tf}.parquet 是否包含 `view` 列？若同一周期有多个视图（不同滤波器参数），是否通过 `view` 区分还是存不同文件？单文件多 view 查询方便但列数膨胀；多文件按 view 拆分结构清晰但文件数多。
- [ ] **bar_index 跨周期语义**：不同周期的 `bar_index` 无对齐关系，是否需要在 signals 文件中额外存储 `session_bar_index`（全局递增）作为跨周期对齐的辅助列？
- [ ] **events.jsonl 粒度**：当前 events.jsonl 仅包含 BS 变更事件。是否需要扩展到 schmitt 信号变更事件（sig 翻转）和交易事件（trade_open/trade_close）？扩展后事件流更完整但文件更大。
- [ ] **Session 元数据**：参数组合是编码在 session_id 中还是单独 `session_meta.parquet`？编码在目录名简单但解析依赖约定；单独文件结构化但多一次 join。
- [ ] **timestamp 冗余**：trades.parquet 不存储时间戳（仅 bar_index），分析时需 join signals 获取时间。是否在 trades.parquet 中冗余 `entry_time` / `exit_time`？冗余后单表查询方便但浪费存储且需维护一致性。
