# 回测数据分析示例

> 基于方案设计中的数据存储结构，展示典型分析场景的代码示意。每个示例包含场景描述、可运行的伪代码/SQL、预期输出形式。
> 目标：帮助读者判断"按最小周期步长存储全量回测数据"的方案是否满足分析需求，以及需要调整什么。

## 2. 数据加载示例

### 2.1 单 Session 加载

场景：加载某一个 ticker 某次回测的 bars 数据，做内存分析。

```python
import polars as pl

# 单 Session 加载 — 指定 ticker 和 session_id
df = pl.read_parquet("data/AAPL/sess_20240701_001/bars.parquet")
print(df.columns)
# → ['bar_index', 'timestamp', 'open', 'high', 'low', 'close', 'volume',
#    'v0_filtered', 'v0_signal', 'v0_position', 'v0_pnl',
#    'v1_filtered', 'v1_signal', 'v1_position', 'v1_pnl',
#    'v2_filtered', 'v2_signal', 'v2_position', 'v2_pnl',
#    'v3_filtered', 'v3_signal', 'v3_position', 'v3_pnl']
```

### 2.2 跨 Session 聚合

场景：汇总某个 ticker 在所有 session 中的表现，无需手动拼接文件。

```sql
-- DuckDB glob 直接读取目录下所有 bars.parquet
SELECT
    regexp_extract(filename, '/(sess_[^/]+)/', 1) AS session_id,
    count(*)                     AS bar_count,
    sum(v0_pnl)                  AS total_pnl,
    avg(abs(v0_signal))          AS signal_density,
    count(DISTINCT bar_index)    AS unique_bars
FROM read_parquet('data/AAPL/*/bars.parquet', filename=true)
GROUP BY session_id
ORDER BY total_pnl DESC;
```

预期输出：每个 session 一行汇总，立即看出哪些 session 盈利、信号密度是否异常。

### 2.3 按时间范围过滤

场景：只加载 2024 年 Q1 的数据，利用 Parquet 谓词下推减少 IO。

```python
# Polars 下推 timestamp 过滤到 Parquet 层，只读相关 row group
df = pl.scan_parquet("data/AAPL/*/bars.parquet").filter(
    pl.col("timestamp").is_between(
        datetime(2024, 1, 1), datetime(2024, 3, 31)
    )
).collect()
```

## 3. 图表回放 — 从存储数据重建可视化

场景：不用 Streamlit，纯 Python 脚本从 Parquet 重建 K 线 + 滤波 + 信号多子图，验证可视化还原度。

```python
import plotly.graph_objects as go
from plotly.subplots import make_subplots

df = pl.read_parquet("data/AAPL/sess_20240701_001/bars.parquet").to_pandas()

fig = make_subplots(
    rows=4, cols=1, shared_xaxes=True,
    row_heights=[0.5, 0.2, 0.15, 0.15],
    subplot_titles=["K线 & 滤波", "信号", "持仓", "PnL"]
)

# 子图1: K线 + 滤波值
fig.add_trace(go.Candlestick(
    x=df["timestamp"], open=df["open"], high=df["high"],
    low=df["low"], close=df["close"], name="K线"
), row=1, col=1)
fig.add_trace(go.Scatter(
    x=df["timestamp"], y=df["v0_filtered"], name="v0滤波", line=dict(width=1)
), row=1, col=1)

# 子图2: 信号值
fig.add_trace(go.Scatter(
    x=df["timestamp"], y=df["v0_signal"], name="v0信号", line=dict(width=1)
), row=2, col=1)

# 子图3: 持仓掩码 (0/1 阶梯)
fig.add_trace(go.Scatter(
    x=df["timestamp"], y=df["v0_position"], name="v0持仓",
    line=dict(shape="hv", width=1)
), row=3, col=1)

# 子图4: 累计 PnL
fig.add_trace(go.Scatter(
    x=df["timestamp"], y=df["v0_pnl"].cumsum(), name="累计PnL"
), row=4, col=1)

fig.update_layout(height=900, xaxis_rangeslider_visible=False)
fig.show()
```

要点：只要 bars.parquet 存储了每 bar 的滤波值、信号、持仓掩码和 PnL，就能 100% 还原回测时的可视化，无需重跑回测。

## 4. 交易分析

### 4.1 交易统计

场景：快速计算胜率、盈亏比、最大回撤等核心指标。

```sql
SELECT
    count(*)                              AS trade_count,
    sum(CASE WHEN pnl > 0 THEN 1 ELSE 0 END) * 1.0 / count(*) AS win_rate,
    avg(CASE WHEN pnl > 0 THEN pnl END)   AS avg_win,
    avg(CASE WHEN pnl < 0 THEN pnl END)   AS avg_loss,
    abs(avg_win / avg_loss)               AS profit_factor,
    max(drawdown)                         AS max_drawdown
FROM (
    SELECT
        pnl,
        pnl - max(pnl) OVER (ORDER BY exit_time ROWS UNBOUNDED PRECEDING) AS drawdown
    FROM read_parquet('data/AAPL/*/trades.parquet')
);
```

### 4.2 逐笔交易审查

场景：找出亏损最大的 10 笔交易，检查入场/出场时机。

```sql
SELECT
    entry_time, exit_time, side, entry_price, exit_price,
    pnl, pnl_pct, entry_reason, exit_reason
FROM read_parquet('data/AAPL/*/trades.parquet')
ORDER BY pnl ASC
LIMIT 10;
```

预期输出：每笔亏损交易的入场原因、持仓时长、亏损幅度，便于定位策略缺陷。

### 4.3 按时间段/周期分组统计

场景：按月份查看策略表现是否稳定。

```sql
SELECT
    strftime(exit_time, '%Y-%m')          AS month,
    count(*)                              AS trades,
    sum(pnl)                              AS monthly_pnl,
    sum(CASE WHEN pnl > 0 THEN 1 ELSE 0 END) * 1.0 / count(*) AS win_rate
FROM read_parquet('data/AAPL/*/trades.parquet')
GROUP BY month
ORDER BY month;
```

## 5. 跨周期对比

### 5.1 信号一致性分析

场景：检查日线和 60 分钟线在同一时刻是否存在矛盾信号（一个做多一个做空）。

```sql
-- 假设 v0=日线, v1=60分钟线
SELECT
    timestamp,
    v0_signal, v1_signal,
    CASE WHEN v0_signal * v1_signal < 0 THEN 'CONFLICT' ELSE 'OK' END AS status
FROM read_parquet('data/AAPL/sess_20240701_001/bars.parquet')
WHERE v0_signal != 0 AND v1_signal != 0
  AND v0_signal * v1_signal < 0;
```

预期输出：列出所有信号矛盾的时间点，帮助评估多周期策略的一致性。

### 5.2 粗周期信号在细周期上的实际表现

```sql
-- 日线信号发出后，60分钟线的实际走势
WITH daily_signals AS (
    SELECT date_trunc('day', timestamp) AS trade_date, v0_signal
    FROM read_parquet('data/AAPL/*/bars.parquet')
    WHERE v0_signal != 0
)
SELECT
    d.trade_date,
    d.v0_signal                                         AS daily_direction,
    sum(b.v1_pnl)                                       AS intraday_pnl,
    sum(CASE WHEN sign(b.v1_signal) = sign(d.v0_signal) THEN 1 ELSE 0 END)
        * 1.0 / count(*)                                AS alignment_ratio
FROM daily_signals d
JOIN read_parquet('data/AAPL/*/bars.parquet') b
  ON date_trunc('day', b.timestamp) = d.trade_date
GROUP BY d.trade_date, d.v0_signal;
```

## 6. 批量回测对比

### 6.1 跨 Session 查询

```sql
-- 汇总所有 session，按 ticker 和参数分组
SELECT
    regexp_extract(filename, '/([^/]+)/[^/]+/bars\.parquet$', 1) AS ticker,
    regexp_extract(filename, '/(sess_[^/]+)/', 1)                 AS session_id,
    sum(v0_pnl)                                                   AS total_pnl,
    stddev(v0_pnl)                                                AS pnl_volatility,
    sum(v0_pnl) / nullif(stddev(v0_pnl), 0) * sqrt(252)           AS sharpe_approx,
    min(v0_pnl)                                                   AS worst_bar
FROM read_parquet('data/*/*/bars.parquet', filename=true)
GROUP BY ticker, session_id;
```

### 6.2 找出最佳参数组合

```sql
-- 跨所有 session 按 sharpe 排序
SELECT *
FROM session_summary   -- 假设已有上一步结果写入表或视图
ORDER BY sharpe_approx DESC
LIMIT 10;
```

### 6.3 参数敏感性热力图示意

```python
import plotly.express as px

# 假设 session_id 编码了参数信息，或从单独的参数元数据表 join
summary = duckdb.sql("""
    SELECT param_a, param_b, avg(sharpe_approx) AS avg_sharpe
    FROM session_summary
    JOIN param_meta USING (session_id)
    GROUP BY param_a, param_b
""").df()

pivot = summary.pivot(index="param_a", columns="param_b", values="avg_sharpe")
fig = px.imshow(pivot, text_auto=".2f", title="参数敏感性: Sharpe")
fig.show()
```

## 7. 数据质量检查

### 7.1 bar_index 连续性校验

```sql
-- 检测每个 session 内 bar_index 是否连续
SELECT
    filename,
    count(*)                          AS bar_count,
    max(bar_index) - min(bar_index) + 1 AS expected_count,
    expected_count - bar_count        AS missing_bars
FROM read_parquet('data/AAPL/*/bars.parquet', filename=true)
GROUP BY filename
HAVING missing_bars > 0;
```

### 7.2 多周期时间对齐检查

```sql
-- 检查不同周期视图的 timestamp 是否对齐（同 bar_index 下各视图 timestamp 应一致）
SELECT bar_index,
       count(DISTINCT timestamp) AS ts_variants
FROM (
    SELECT bar_index, timestamp FROM read_parquet('data/AAPL/*/bars.parquet')
    -- 若有单独的多周期时间列，改为 UNPIVOT
)
GROUP BY bar_index
HAVING ts_variants > 1;
```

## 8. 待讨论

以下设计选择需要确认，直接影响存储方案和分析效率：

- [ ] **列命名规范**：用 `v0_filtered` / `v1_filtered` 还是 `日线_filtered` / `60min_filtered`？前者紧凑适合代码循环，后者自解释适合协作。
- [ ] **宽表 vs 窄表**：bars.parquet 是否需要包含所有周期的所有列？宽表查询简单但列多（4 周期 x 4 列 = +16 列），窄表（bar_index + view_id + 指标列）省存储但查询需 pivot。
- [ ] **写入策略**：实时写入（每 bar 一次）能支持盘中实时分析，但增加 IO 和碎片；批量写入（session 结束时）简单但丢掉盘中分析能力。
- [ ] **trades 与 bars 合并**：trades.parquet 是否需要冗余 bar_index 或 timestamp 到 bars 行上？合并后单表查询方便但数据重复。
- [ ] **NaN 处理**：分析时是否需要自动 ffill（查阅方便）还是保持原始 NaN？ffill 方便画图但隐含了"未变化"的假设，可能掩盖 bug。
- [ ] **events.jsonl 粒度**：BS 标记变更事件是否需要记录触发原因（止损/止盈/信号翻转/手动）？不记录则无法事后分析平仓原因分布。
- [ ] **Session 元数据**：参数组合是编码在 session_id 中还是单独 `session_meta.parquet`？编码在目录名简单但解析依赖约定；单独文件结构化但多一次 join。
