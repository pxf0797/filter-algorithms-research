# 回测数据分析示例

> 基于统一宽表 `backtest_result.parquet`，展示从加载到对比的完整分析链路。每节包含场景描述、可运行 SQL / 伪代码、预期输出示意。
>
> **核心数据模型**：一张宽表，每行 = 一个 `_min_tf` bar 时刻。固定列标识时间轴，其余列按视图（v0~v3）组织。粗周期（日线）信号在多个 min_tf 行上自然重复——这是 feature，不是 bug。

## 1. 环境准备

```bash
pip install duckdb pandas polars pyarrow
```

核心依赖：DuckDB 做跨 Session 聚合查询，Polars 做单 Session 高性能加载，PyArrow 做 Parquet 底层读写。

## 2. 数据加载

### 2.1 Schema 速览

`backtest_result.parquet` 的列结构如下：

**固定列**（每行一个值）：

| 列名 | 类型 | 说明 |
|------|------|------|
| `bar_index` | int32 | 全局 bar 序号（基于 `_min_tf` 递增） |
| `bar_timestamp` | str | bar 时间戳，格式 `YYYY-MM-DD HH:MM:SS` |

**每视图列**（v0~v3，4 组，共 7x4=28 列）：

| 列名模式 | 类型 | 说明 |
|----------|------|------|
| `{view}_sig` | int8 | 信号值：+1 做多，-1 做空，0 空仓 |
| `{view}_pnl_long` | float32 | 做多方向累计 PnL（该 bar 时刻的值） |
| `{view}_pnl_short` | float32 | 做空方向累计 PnL |
| `{view}_long_pos` | bool | 是否持有多头仓位 |
| `{view}_short_pos` | bool | 是否持有空头仓位 |
| `{view}_trade` | str | 交易事件标记：`"B"` 买入，`"S"` 卖出，`""` 无交易 |
| `{view}_bs_entry` | str | BS 入场标记（如 `"B0"`, `"S1"`, `""`) |
| `{view}_bs_exit` | str | BS 出场标记（如 `"X0"`, `""`) |

**粗周期重复说明**：回测的 `_min_tf` 是最细粒度（如 5 分钟）。日线信号在每个 5 分钟 bar 上都会存一份相同的值，直到下一根日线 bar 到来。因此日线 PnL 列在 5 分钟行上看是"阶梯状"的——这不是数据错误，而是粗周期信号在细时间轴上的自然投影。

## 3. 信号分析

> 基于视图的 `{view}_sig` 列进行信号状态统计。sig 为 int8 类型，取值 +1（做多）、-1（做空）、0（空仓）。

### 3.1 信号翻转检测

场景：统计 v0 视图的信号翻转频率——sig 从 +1 变 -1（或反之）的次数，评估策略交易频率是否合理。

```sql
-- DuckDB：检测 v0 信号的翻转点
WITH signal_changes AS (
    SELECT
        bar_index,
        bar_timestamp,
        v0_sig,
        LAG(v0_sig) OVER (ORDER BY bar_index) AS prev_sig,
        CASE
            WHEN v0_sig * LAG(v0_sig) OVER (ORDER BY bar_index) < 0 THEN 1
            ELSE 0
        END AS flipped
    FROM read_parquet('data/AAPL/sess_20240701_001/backtest_result.parquet')
)
SELECT
    count(*)                                   AS total_bars,
    sum(flipped)                               AS flip_count,
    sum(flipped) * 1.0 / count(*)              AS flip_rate,
    count(*) * 1.0 / nullif(sum(flipped), 0)   AS bars_per_flip
FROM signal_changes;
```

预期输出：若 total_bars=10000（5min 粒度），flip_count=50~100，flip_rate=0.5%~1%，bars_per_flip=100~200。翻转率过高可能意味着信号频繁抖动。

### 3.2 多空时间占比

场景：统计 v0 信号在多、空、空仓三种状态下的时间占比，检查策略是否存在方向偏差。

```sql
SELECT
    sum(CASE WHEN v0_sig > 0 THEN 1 ELSE 0 END) * 1.0 / count(*) AS long_signal_ratio,
    sum(CASE WHEN v0_sig < 0 THEN 1 ELSE 0 END) * 1.0 / count(*) AS short_signal_ratio,
    sum(CASE WHEN v0_sig = 0 THEN 1 ELSE 0 END) * 1.0 / count(*) AS neutral_ratio,
    -- 实际持仓比例（position 为 True 的 bar）
    sum(CASE WHEN v0_long_pos THEN 1 ELSE 0 END)  * 1.0 / count(*) AS long_holding_ratio,
    sum(CASE WHEN v0_short_pos THEN 1 ELSE 0 END) * 1.0 / count(*) AS short_holding_ratio
FROM read_parquet('data/AAPL/sess_20240701_001/backtest_result.parquet');
```

预期输出：若多空信号比例约 45:45（剩余 10% 空仓），策略无明显方向偏好。若偏斜超过 70:30，需要检查策略逻辑。

### 3.3 信号持续期分布

场景：分析每次连续同号信号的持续 bar 数分布，识别是否存在频繁抖动（短持续期占比过高）。

```sql
-- 计算 v0 信号的持续 bar 数分布
WITH sig_groups AS (
    SELECT
        bar_index,
        v0_sig,
        SUM(CASE
            WHEN v0_sig * LAG(v0_sig) OVER (ORDER BY bar_index) < 0
              OR LAG(v0_sig) OVER (ORDER BY bar_index) IS NULL
            THEN 1 ELSE 0
        END) OVER (ORDER BY bar_index) AS run_id
    FROM read_parquet('data/AAPL/sess_20240701_001/backtest_result.parquet')
    WHERE v0_sig != 0
),
run_lengths AS (
    SELECT run_id, count(*) AS duration, MAX(v0_sig) AS direction
    FROM sig_groups
    GROUP BY run_id
)
SELECT
    CASE WHEN direction > 0 THEN 'long' ELSE 'short' END AS signal_type,
    count(*)                                              AS run_count,
    avg(duration)                                         AS avg_duration,
    median(duration)                                      AS median_duration,
    min(duration)                                         AS min_duration,
    max(duration)                                         AS max_duration,
    sum(CASE WHEN duration <= 3 THEN 1 ELSE 0 END) * 1.0 / count(*) AS short_run_ratio
FROM run_lengths
GROUP BY signal_type
ORDER BY signal_type;
```

预期输出：short_run_ratio 低于 20% 说明信号稳定；超过 30% 说明存在频繁抖动，可能需要增大 schmitt 阈值或调整滤波参数。

### 3.4 多视图信号一致性速览

场景：同一 bar 时刻，比较 v0 和 v1 的信号方向是否一致。

```sql
SELECT
    count(*)                                                  AS total_bars,
    sum(CASE WHEN v0_sig * v1_sig < 0 THEN 1 ELSE 0 END)     AS conflict_bars,
    conflict_bars * 1.0 / total_bars                          AS conflict_ratio
FROM read_parquet('data/AAPL/sess_20240701_001/backtest_result.parquet')
WHERE v0_sig != 0 AND v1_sig != 0;
```

预期输出：conflict_ratio < 5% 为正常，说明不同参数设置的视图在大多数时候方向一致。若 > 15%，需要检查参数差异是否过大。

## 4. 跨周期一致性

> 同一回测中，粗周期（如日线）信号与细周期（如 60 分钟）信号在同一 min_tf 行上并存。本节分析两者的一致性与差异。

**重要前提**：粗周期信号在多个 min_tf 行上自然重复。例如日线 sig 在 09:30 到 16:00 的所有 5 分钟 bar 上都是同一个值。这不是矛盾，而是粗周期信号在细时间轴上的投影。当我们在同一 min_tf 行上发现"日线 sig=+1 但 60 分钟 sig=-1"时，这反映的是不同周期对市场的不同判断——粗周期信号"滞后"是其内在属性，不代表数据错误。

### 4.1 矛盾行检测

场景：假设 v0 是日线视图，v1 是 60 分钟视图。找出同一 min_tf 行上两者信号方向相反的行。

```sql
-- 检测同一行上日线(v0)和60分钟(v1)信号方向矛盾的行
SELECT
    bar_index,
    bar_timestamp,
    v0_sig AS daily_sig,
    v1_sig AS hourly_sig,
    v0_pnl_long  AS daily_pnl_long,
    v1_pnl_long  AS hourly_pnl_long
FROM read_parquet('data/AAPL/sess_20240701_001/backtest_result.parquet')
WHERE v0_sig != 0
  AND v1_sig != 0
  AND v0_sig * v1_sig < 0
ORDER BY bar_index
LIMIT 20;
```

预期输出：列出矛盾行。这些行集中出现在趋势转折点附近——日线信号尚未翻转（仍保持原方向），而 60 分钟信号已经率先翻转。这是正常的周期滞后现象。

### 4.2 矛盾行占比与时间分布

场景：统计矛盾行总数和占比，以及它们在一日内的分布规律。

```sql
WITH conflicts AS (
    SELECT
        bar_index,
        bar_timestamp,
        CASE WHEN v0_sig * v1_sig < 0 THEN 1 ELSE 0 END AS is_conflict
    FROM read_parquet('data/AAPL/sess_20240701_001/backtest_result.parquet')
    WHERE v0_sig != 0 AND v1_sig != 0
)
SELECT
    sum(is_conflict)                                               AS conflict_count,
    count(*)                                                       AS total_overlap_bars,
    sum(is_conflict) * 1.0 / count(*)                             AS conflict_ratio
FROM conflicts;
```

```sql
-- 矛盾行的小时分布（看集中在哪些时段）
SELECT
    substr(bar_timestamp, 12, 2) AS hour_of_day,
    count(*)                     AS conflict_count
FROM read_parquet('data/AAPL/sess_20240701_001/backtest_result.parquet')
WHERE v0_sig != 0
  AND v1_sig != 0
  AND v0_sig * v1_sig < 0
GROUP BY hour_of_day
ORDER BY hour_of_day;
```

预期输出：矛盾行多集中在开盘后 30 分钟和收盘前 30 分钟——这些时段细周期信号变化快，粗周期尚未跟上。

### 4.3 粗周期信号在细周期上的 PnL 表现

场景：按日聚合，看日线信号方向在当天 60 分钟级别上产生的实际日内 PnL。

```sql
-- 按日期聚合：日线信号 vs 当天 60 分钟的日内 PnL
SELECT
    substr(bar_timestamp, 1, 10) AS trade_date,
    MAX(v0_sig)                  AS daily_sig,   -- 粗周期信号（当天不变）
    SUM(v1_pnl_long)             AS intraday_pnl_long,
    SUM(v1_pnl_short)            AS intraday_pnl_short,
    count(*)                     AS min_tf_bars
FROM read_parquet('data/AAPL/sess_20240701_001/backtest_result.parquet')
WHERE v0_sig != 0
GROUP BY trade_date
ORDER BY trade_date;
```

预期输出：对比 `daily_sig` 方向与 `intraday_pnl_long/short` 的符号。若日线看多但日内 PnL 为负大量出现，说明日线信号在日内层面有滞后损耗。

## 5. PnL 分析

> 基于 `{view}_pnl_long` 和 `{view}_pnl_short` 列，分析各视图的盈亏表现。PnL 值为累计值——每个 bar 行记录的是到该时刻为止的累计盈亏。

### 5.2 最大回撤计算（SQL 窗口函数）

场景：从累计 PnL 序列计算最大回撤（MDD）——累计 PnL 从历史峰值的最大跌幅。

```sql
-- 计算 v0 的最大回撤
WITH pnl_series AS (
    SELECT
        bar_index,
        bar_timestamp,
        v0_pnl_long + v0_pnl_short AS pnl_total
    FROM read_parquet('data/AAPL/sess_20240701_001/backtest_result.parquet')
),
with_peak AS (
    SELECT
        bar_index,
        bar_timestamp,
        pnl_total,
        MAX(pnl_total) OVER (ORDER BY bar_index
            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS peak_value
    FROM pnl_series
),
drawdowns AS (
    SELECT
        bar_index,
        bar_timestamp,
        pnl_total,
        peak_value,
        pnl_total - peak_value AS drawdown,
        (pnl_total - peak_value) / nullif(peak_value, 0) AS drawdown_pct
    FROM with_peak
)
SELECT
    min(drawdown)                             AS max_drawdown_abs,
    min(drawdown_pct)                         AS max_drawdown_pct,
    -- 回撤起止时间
    (SELECT bar_timestamp FROM drawdowns
     WHERE drawdown_pct = (SELECT min(drawdown_pct) FROM drawdowns)
     LIMIT 1)                                 AS mdd_time
FROM drawdowns;
```

预期输出：一行，包含最大回撤绝对值和百分比，以及发生时间。若 MDD > 20%，策略风险较大。

### 5.3 做多 vs 做空收益对比

场景：对比同一视图下做多和做空的最终累计收益，判断策略的 alpha 来源。

```sql
SELECT
    -- v0
    MAX(v0_pnl_long)                       AS v0_long_final,
    MAX(v0_pnl_short)                      AS v0_short_final,
    MAX(v0_pnl_long) + MAX(v0_pnl_short)   AS v0_total_final,
    -- v1
    MAX(v1_pnl_long)                       AS v1_long_final,
    MAX(v1_pnl_short)                      AS v1_short_final,
    MAX(v1_pnl_long) + MAX(v1_pnl_short)   AS v1_total_final
FROM read_parquet('data/AAPL/sess_20240701_001/backtest_result.parquet');
```

预期输出：一行对比 v0 和 v1 的多空收益。若 long 远大于 short（或反之），说明策略收益有方向偏好，需要检查是否存在市场趋势偏差。

### 5.4 各视图 PnL 汇总对比

## 6. 交易分析

> 基于 `{view}_trade` 列分析交易事件。trade 值为 `"B"`（买入开仓）或 `"S"`（卖出平仓/开空），空字符串 `""` 表示无交易。

### 6.1 交易频率统计

场景：统计各视图的交易笔数（B 和 S 分开计）。

```sql
SELECT
    'v0' AS view,
    sum(CASE WHEN v0_trade = 'B' THEN 1 ELSE 0 END) AS buy_count,
    sum(CASE WHEN v0_trade = 'S' THEN 1 ELSE 0 END) AS sell_count,
    count(*) AS total_bars
FROM read_parquet('data/AAPL/sess_20240701_001/backtest_result.parquet')
UNION ALL
SELECT
    'v1', sum(CASE WHEN v1_trade = 'B' THEN 1 ELSE 0 END),
    sum(CASE WHEN v1_trade = 'S' THEN 1 ELSE 0 END), count(*)
FROM read_parquet('data/AAPL/sess_20240701_001/backtest_result.parquet')
UNION ALL
SELECT
    'v2', sum(CASE WHEN v2_trade = 'B' THEN 1 ELSE 0 END),
    sum(CASE WHEN v2_trade = 'S' THEN 1 ELSE 0 END), count(*)
FROM read_parquet('data/AAPL/sess_20240701_001/backtest_result.parquet')
UNION ALL
SELECT
    'v3', sum(CASE WHEN v3_trade = 'B' THEN 1 ELSE 0 END),
    sum(CASE WHEN v3_trade = 'S' THEN 1 ELSE 0 END), count(*)
FROM read_parquet('data/AAPL/sess_20240701_001/backtest_result.parquet');
```

预期输出：4 行，每行一个视图的买卖次数。若 B 和 S 数量相差超过 1，说明存在未匹配的开仓或平仓（需检查数据完整性）。

### 6.2 交易间隔分布

场景：统计两次相邻交易的 bar 间隔，评估交易节奏。

```sql
-- 计算 v0 交易事件之间的 bar 间隔
WITH trade_bars AS (
    SELECT
        bar_index,
        v0_trade,
        ROW_NUMBER() OVER (ORDER BY bar_index) AS rn
    FROM read_parquet('data/AAPL/sess_20240701_001/backtest_result.parquet')
    WHERE v0_trade != ''
),
trade_gaps AS (
    SELECT
        bar_index,
        v0_trade,
        bar_index - LAG(bar_index) OVER (ORDER BY bar_index) AS bars_since_last_trade
    FROM trade_bars
)
SELECT
    avg(bars_since_last_trade)     AS avg_gap,
    median(bars_since_last_trade)  AS median_gap,
    min(bars_since_last_trade)     AS min_gap,
    max(bars_since_last_trade)     AS max_gap
FROM trade_gaps
WHERE bars_since_last_trade IS NOT NULL;
```

预期输出：若 min_gap=1（连续两根 bar 都有交易），说明存在连续开仓；max_gap 过大说明有长时间无交易的区间。

### 6.3 连续开仓检测

场景：检测连续两根 bar 都出现 B（连续开多）的异常情况。

```sql
-- 检测 v0 连续开仓（连续两个 B 没有中间的 S）
WITH trades_only AS (
    SELECT
        bar_index,
        bar_timestamp,
        v0_trade,
        LAG(v0_trade) OVER (ORDER BY bar_index) AS prev_trade
    FROM read_parquet('data/AAPL/sess_20240701_001/backtest_result.parquet')
    WHERE v0_trade != ''
)
SELECT
    bar_index,
    bar_timestamp,
    prev_trade,
    v0_trade
FROM trades_only
WHERE v0_trade = 'B' AND prev_trade = 'B'
   OR v0_trade = 'S' AND prev_trade = 'S'  -- 连续平仓也检测
ORDER BY bar_index
LIMIT 20;
```

预期输出：连续开仓行列表。正常情况下 B 和 S 应交替出现（B→S→B→S）。若出现连续 B，说明存在加仓逻辑或信号异常；连续 S 同理。

### 6.4 交易时段分布

场景：统计交易在各小时段的分布，识别策略是否在特定时段过于活跃。

```sql
SELECT
    substr(bar_timestamp, 12, 2) AS hour_of_day,
    sum(CASE WHEN v0_trade != '' THEN 1 ELSE 0 END) AS v0_trades,
    sum(CASE WHEN v1_trade != '' THEN 1 ELSE 0 END) AS v1_trades
FROM read_parquet('data/AAPL/sess_20240701_001/backtest_result.parquet')
GROUP BY hour_of_day
ORDER BY hour_of_day;
```

预期输出：交易集中在开盘（9-10 点）和收盘（15-16 点）时段是常见现象。若午盘（11:30-13:00）仍有大量交易，需检查是否为数据错误。

## 7. BS 标记与信号对照

> 基于 `{view}_bs_entry` 和 `{view}_bs_exit` 列，分析 BS（买卖）入场/出场标记与信号的一致性。

### 7.1 BS 入场标记与信号方向对照

场景：检查每个 BS 入场标记出现时，对应视图的信号值是否匹配。B 类入场（如 `B0`）应与 sig=+1 匹配，S 类入场（如 `S1`）应与 sig=-1 匹配。

```sql
-- 检查 v0 的 BS 入场标记和信号值是否匹配
SELECT
    bar_index,
    bar_timestamp,
    v0_sig,
    v0_bs_entry,
    CASE
        WHEN v0_bs_entry LIKE 'B%' AND v0_sig <= 0 THEN 'MISMATCH: B entry but sig不是+1'
        WHEN v0_bs_entry LIKE 'S%' AND v0_sig >= 0 THEN 'MISMATCH: S entry but sig不是-1'
        ELSE 'OK'
    END AS check_result
FROM read_parquet('data/AAPL/sess_20240701_001/backtest_result.parquet')
WHERE v0_bs_entry != ''
  AND check_result != 'OK'
ORDER BY bar_index;
```

预期输出：理想情况下返回 0 行。若出现不匹配行，说明 BS 标记逻辑与信号生成逻辑存在偏差。

### 7.2 BS 出场标记与仓位状态对照

场景：检查 BS 出场标记（如 `X0`）出现时，仓位是否确实从有仓变为无仓。

```sql
SELECT
    bar_index,
    bar_timestamp,
    v0_bs_exit,
    v0_long_pos,
    v0_short_pos,
    LAG(v0_long_pos) OVER (ORDER BY bar_index)  AS prev_long_pos,
    LAG(v0_short_pos) OVER (ORDER BY bar_index) AS prev_short_pos
FROM read_parquet('data/AAPL/sess_20240701_001/backtest_result.parquet')
WHERE v0_bs_exit != ''
  AND (
      -- 出场标记出现时，之前有仓位，当前也没有仓位保留（正常的平仓）
      (LAG(v0_long_pos) OVER (ORDER BY bar_index) = false
       AND LAG(v0_short_pos) OVER (ORDER BY bar_index) = false)
  )
ORDER BY bar_index
LIMIT 20;
```

预期输出：列出出场标记出现但前一根 bar 并无可平仓位的异常情况。若返回 0 行，出场逻辑正确。

### 7.3 BS 标记统计

场景：按视图汇总 BS 入场标记的类型（B0, B1, S0, S1 等）和数量。

```sql
SELECT 'v0' AS view, v0_bs_entry AS bs_type, count(*) AS cnt
FROM read_parquet('data/AAPL/sess_20240701_001/backtest_result.parquet')
WHERE v0_bs_entry != ''
GROUP BY v0_bs_entry
UNION ALL
SELECT 'v1', v1_bs_entry, count(*)
FROM read_parquet('data/AAPL/sess_20240701_001/backtest_result.parquet')
WHERE v1_bs_entry != ''
GROUP BY v1_bs_entry;
-- ... v2, v3 同理
```

预期输出：每个视图的 BS 标记类型分布，用于检查各标记的出现频率是否合理。

## 9. 数据质量检查

> 对 `backtest_result.parquet` 进行完整性、一致性校验。

### 9.1 bar_index 连续性检查

场景：确保 bar_index 从 0 开始连续递增，无间断。

```sql
SELECT
    filename,
    count(*)                            AS bar_count,
    max(bar_index) - min(bar_index) + 1 AS expected_count,
    expected_count - bar_count          AS missing_bars
FROM read_parquet('data/AAPL/*/backtest_result.parquet', filename=true)
GROUP BY filename
HAVING missing_bars > 0;
```

预期输出：返回 0 行表示所有文件的 bar_index 连续。若有行返回，说明存在数据缺失或索引跳跃，需要排查回测写入逻辑。

### 9.2 粗周期信号重复性校验

场景：验证粗周期（日线）信号在相同日期的所有 min_tf 行上值一致（信号未被错误修改）。

```sql
-- 检查 v0（假设为日线）在同一日期内信号是否恒定
SELECT
    substr(bar_timestamp, 1, 10) AS trade_date,
    count(DISTINCT v0_sig)       AS distinct_sig_count,
    count(*)                     AS bar_count
FROM read_parquet('data/AAPL/sess_20240701_001/backtest_result.parquet')
GROUP BY trade_date
HAVING distinct_sig_count > 1
ORDER BY trade_date;
```

预期输出：返回 0 行——同一天内日线信号应只有一个值。若返回行，说明日线信号在同一天内被修改，这是真正的数据错误。

### 9.3 trade 事件完整性检查

场景：验证每对 B 和 S 是否匹配（trade 列中 B 和 S 数量相等）。

```sql
SELECT
    sum(CASE WHEN v0_trade = 'B' THEN 1 ELSE 0 END) AS buy_count,
    sum(CASE WHEN v0_trade = 'S' THEN 1 ELSE 0 END) AS sell_count,
    buy_count - sell_count                           AS imbalance
FROM read_parquet('data/AAPL/sess_20240701_001/backtest_result.parquet');
```

预期输出：imbalance=0 或 ±1（允许末尾未平仓）。若 |imbalance| > 1，说明存在未配对的 B 或 S 事件。

### 9.4 仓位状态一致性校验

场景：验证 position 列（long_pos/short_pos）与 sig 列的逻辑一致性。

```sql
-- 检查：sig=0 时不应该有仓位
SELECT
    bar_index,
    bar_timestamp,
    v0_sig,
    v0_long_pos,
    v0_short_pos
```

### 9.5 PnL 单调性校验（针对粗周期）

场景：对于粗周期（日线），PnL 在同一个日期内的 min_tf 行上应该是单调的（因为日线 PnL 按日线 bar 更新）。

```sql
-- 检查 v0 PnL 在同一日内是否单调（粗周期特征）
WITH daily_pnl AS (
    SELECT
        substr(bar_timestamp, 1, 10) AS trade_date,
        bar_index,
        v0_pnl_long + v0_pnl_short    AS pnl_total,
        LAG(v0_pnl_long + v0_pnl_short) OVER (
            PARTITION BY substr(bar_timestamp, 1, 10) ORDER BY bar_index
        ) AS prev_pnl
    FROM read_parquet('data/AAPL/sess_20240701_001/backtest_result.parquet')
)
SELECT trade_date, count(*) AS non_monotonic_bars
FROM daily_pnl
WHERE prev_pnl IS NOT NULL AND pnl_total != prev_pnl
GROUP BY trade_date
HAVING count(*) > 0
ORDER BY trade_date;
```

**说明**：粗周期 PnL 在同一天内不会每个 min_tf 都变——它只在日线 bar 结束时更新一次。因此同一日内大多数行的 PnL 值相同。若同一日内 PnL 多次变化（non_monotonic_bars 很大），说明该周期不是真正粗周期，或者存在数据写入问题。

## 10. 待讨论

以下设计选择需要确认，直接影响存储方案和分析效率：

- [ ] **view 命名规范**：当前视图固定命名为 v0~v3。是否需要支持自定义视图名称（如 `ma_cross_v0`、`rsi_v1`）？自定义名称更直观但列名变长，且解析 view 时失去固定模式。
- [ ] **trade 列粒度**：当前 trade 只有 `B` 和 `S` 两种值。是否需要区分 `B_OPEN`（开多）、`B_CLOSE`（平空）、`S_OPEN`（开空）、`S_CLOSE`（平多）？更细粒度便于区分开仓和平仓，但增加了解析复杂度。
- [ ] **bs_entry/bs_exit 的值域规范**：当前 `B0`/`S1`/`X0` 等标记的命名约定是什么？是否有统一的枚举定义文档？缺少规范容易导致不同 Session 使用不一致的标记。
- [ ] **是否需要存储 bar 级别 PnL 增量**：当前 PnL 是累计值。是否需要额外存储 `{view}_pnl_long_delta`（当前 bar 的 PnL 变化量）？增量值便于计算单 bar 收益分布，但增加了列数（每视图 +2 列）。
- [ ] **粗周期信号标注**：当前无法从数据本身区分哪个 view 是粗周期、哪个是细周期。是否需要额外的元数据（如单独的 `session_meta.parquet`）记录每个 view 对应的周期？还是完全依赖 Session 目录命名约定？
- [ ] **CSV 导出的必要性**：是否需要支持 Parquet → CSV 的自动转换（作为可选输出）？CSV 方便人工快速浏览但文件体积大（约为 Parquet 的 5-10 倍），且无类型信息。
- [ ] **timestamp 格式**：当前 `bar_timestamp` 为字符串类型。是否应该用 DuckDB 的 `TIMESTAMP` 或 `DATETIME` 类型？字符串便于可读性，但时间比较和范围查询效率低于原生时间类型。
- [ ] **bar_index 的参考系**：`bar_index` 是基于 `_min_tf` 的全局序号。是否需要额外存储 `session_bar_index`（Session 内部从 0 开始的独立序号）？当多个 Session 的数据合并时，`bar_index` 会重复（每个 Session 都从自己回测起点开始编号），跨 Session 分析时需要额外处理。
