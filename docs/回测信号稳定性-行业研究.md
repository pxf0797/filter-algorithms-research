## 1. 摘要

### 问题本质

量化回测系统的信号不稳定性，其根源在于**非因果滤波器在滑动窗口上重复计算**，导致历史信号随回测截止日（cutoff_date）的变化而漂移。这不是一个小众 bug，而是触及量化回测最核心的可靠性问题：回测结果是否忠实地模拟了真实交易中可实现的决策序列？

### 行业现状

学术界早已将这一问题形式化——前视偏差（Look-Ahead Bias）、数据窥探（Data Snooping）、非因果滤波的争议——并提供了从 White's Reality Check（2000）到 Lopez de Prado 的 Purged K-Fold（2018）等一系列检测和矫正工具。工业界五大主流平台（QuantConnect/LEAN、Backtrader、Zipline、VectorBT、vnpy）各自以不同架构应对：事件驱动、Pipeline 快照、双列时间戳门控。它们共同遵守一个核心原则——**在任何"已知时间点"冻结信号状态**。

### 核心发现

| 维度 | 发现 |
|------|------|
| 问题定性 | 非因果滤波（`sosfiltfilt`、centered `savgol_filter`）在滑动窗口上重算 = 前视偏差 + 信号重绘（Repainting） |
| 学术共识 | 金融时间序列不存在非因果数据生成过程；前视偏差可导致年化收益高估 8%（Daniel et al., 2009）；7,846 条技术规则经 Reality Check 校正后几乎无幸存 |
| 工业实践 | 所有主流平台通过 Time Frontier / Pipeline 快照 / x+1 执行 / `.shift(1)` 等机制保证"历史信号不可变" |
| 我们方案的定位 | "Snapshot 模式"在概念上等价于 Zipline Pipeline API + QuantConnect Precompute 模式，行业已有成熟先例 |

### 推荐方向

- **短期（1-2 周）：** 因果滤波器替换 + Bar-Close 门控 + Ghost Data Test
- **中期（1-2 月）：** Snapshot 模式完整实施 + Walk-Forward 验证框架
- **长期（3-6 月）：** Point-in-Time 数据架构 + Purged K-Fold 交叉验证

## 2. 问题框架：回测中的信号不稳定性

### 2.1 问题的形式化定义

**信号不稳定性（Signal Instability）** 是指：当回测系统的截止日期 `cutoff_date` 向前推进（或向后回溯）时，在时间点 `t < cutoff_date` 上的历史信号——特别是买卖标记点（BS Points）——发生变化、消失或移位。

其数学形式可表述为：

> 设 `S(t; T)` 为在截止日期 `T` 时计算的 `t` 时刻信号值。当且仅当信号计算满足 **因果性约束**——即 `S(t; T)` 仅依赖于 `{data(\tau) | \tau <= t}`——时，才有：
>
> `S(t; T1) = S(t; T2)` 对所有 `T1, T2 > t` 成立。
>
> 若计算过程中使用了非因果滤波器（如 `filtfilt` 或 centered window），则该恒等式被破坏。

**在我们的系统中，问题由三个因素复合而成：**

1. **非因果滤波器**（`scipy.signal.sosfiltfilt`、`scipy.signal.savgol_filter` 默认 centered 模式）在计算 `t` 时刻信号时使用了 `t + k` 时刻的数据。
2. **滑动窗口机制**：每次回测以 `cutoff_date` 为窗口右边界加载数据。当 `cutoff_date` 变化时，窗口内容变化，非因果滤波器的输出在窗口内所有点——包括远离右边界的历史点——都会改变。
3. **BS 点标记机制**依赖于滤波后的信号形态（如峰值检测），形态变化直接导致标记点跳跃或消失。

这三者产生了我们称之为 **"6 级级联放大效应"** 的现象。

### 2.2 与经典偏误的对应关系

我们的问题同时触及量化金融中三个经典偏误：

| 经典偏误 | 定义 | 在我们的问题中的体现 |
|----------|------|---------------------|
| **前视偏差（Look-Ahead Bias）** | 回测中使用了决策时刻尚不可知的信息 | `filtfilt` 在 `t` 时刻使用了 `t+k` 时刻的价格数据 |
| **数据窥探（Data Snooping）** | 同一数据集被反复用于推断，导致虚假显著性 | 滑动窗口反复重算 → 面对不同 `cutoff_date` 的历史信号是同一数据的多次"试验" |
| **信号重绘（Repainting）** | 历史信号值随新数据到达而改变 | BS 点在 `cutoff_date` 向前推进后位置改变，是 Repainting 的经典症状 |

**前视偏差的量级：** Daniel, Sornette & Wohrmann（2009）发现，仅因使用"当前"指数成分股回测历史，S&P 500 的年化收益就被高估了 **8 个百分点**。在我们的场景中，非因果滤波引入的偏差量级可能更大，因为它直接影响信号生成逻辑的每一个环节。

### 2.3 我们的案例：BS 点跳跃的 6 级级联放大效应

（简要回顾第一份研究报告的发现）

```
Level 1: 非因果滤波器在窗口右边界附近产生"未来信息污染"
   ↓
Level 2: 窗口右边界邻域（最后 N 个数据点）的信号形态发生扭曲
   ↓
Level 3: BS 点检测算法（峰值/阈值）在边界邻域产生错误标记或遗漏
   ↓
Level 4: cutoff_date 移动 → 窗口变化 → Level 1-3 在整个历史序列上重现
   ↓
Level 5: 不同 cutoff_date 的回测结果不可比较（同一历史时期给出不同信号）
   ↓
Level 6: 策略评估失去可靠性基础——无法判断策略是真正盈利还是滤波假象
```

**核心洞察：** 这不是"边界附近的局部扰动"，而是**整个时间序列的全局不稳定性**。非因果滤波器的输出在每一个时间点都依赖于整个窗口数据，因此窗口的任何变化都会改变所有历史输出值。

## 3. 学术视角：已知偏误与形式化框架

### 3.1 前视偏差（Look-Ahead Bias）的学术定义与分类

学术界将前视偏差分为多个子类，每一类在我们的场景中都有对应：

| 子类 | 描述 | 在我们的场景中 |
|------|------|---------------|
| **数据前视（Data Look-Ahead）** | 特征计算使用了未来观测值 | `filtfilt` 的核心问题 |
| **基准前视（Benchmark Look-Ahead）** | 使用"当前"成分股回测历史 | 如果我们的股票池动态变化但未做 PIT 处理 |
| **幸存偏差（Survivorship Bias）** | 仅包含存续至今的资产 | 北美市场回溯 10 年，幸存偏差导致数据遗漏约 75% 的股票 |
| **退市偏差（Delisting Bias）** | 退市回报处理不当 | 深度价值组合年化收益因退市调整从 30.1% 降至 24.6%（Price, Beaver & McNichols） |
| **LLM 前视偏差（Emerging）** | LLM 训练数据包含事后金融信息 | GPT-4o 能以 <1% 误差回忆训练窗口内的 S&P 500 收盘价（Lopez-Lira et al., 2025） |

**检测方法汇总：**

| 方法 | 描述 | 来源 |
|------|------|------|
| **LAP 测试** | Token 级概率分析检测 LLM 预测中的记忆化 | Gao, Jiang & Yan (2026) |
| **Alpha 衰减分析** | 比较样本内外 Alpha；-15 到 -22 pp 的衰减表明前视偏差 | Benhenda (2026) |
| **PIT 对比** | 标准模型 vs PIT 模型（ChronoBERT/ChronoGPT）对比 | He et al. (2025) |
| **匿名化测试** | 去除公司名/日期/代码，比较性能 | Glasserman & Lin (2023) |
| **幽灵数据测试（Ghost Data Test）** | 在序列中间插入人造价格尖峰；若尖峰之前信号变化 = 前视偏差 | 实用技术标准 |

→ **建议：** 在所有回测流程中强制加入 Ghost Data Test 作为前视偏差的冒烟检测。

### 3.2 数据窥探偏误（Data Snooping）与多重检验问题

数据窥探是金融领域多重检验问题的直接体现。当你在同一数据集上测试足够多的策略变体时，仅凭偶然就会出现"显著盈利"的假象：

| 独立检验次数 (m) | 至少一次假阳性概率（alpha = 5%）|
|---|---|
| 1 | 5% |
| 10 | ~40% |
| 50 | ~92% |
| 100 | ~99.4% |
| 7,846（Sullivan et al., 1999） | 接近 100% |

**关键论文及其贡献：**

**White's Reality Check（2000）** 是第一个专门针对策略评估中数据窥探的正式检验：

- **原假设 H0：** 基准模型不劣于任何备选策略
- **检验统计量：** `RC_n = max_k sqrt(n) * d_bar_k`（所有 k 个策略中最大标准化超额收益）
- **方法：** Stationary Bootstrap 保持策略间和时间上的依赖结构
- **局限（Hansen 的批评）：** 使用"最不利配置"（LFC）假设所有策略的期望收益为零，当存在大量差策略时，bootstrap p 值被人为膨胀，导致检验过于保守

**Hansen's Superior Predictive Ability (SPA) Test（2005）** 改进了 White's RC：

- 使用重新中心化的零分布，排除明显差的策略
- 样本依赖的零分布更好地反映了策略性能的真实配置
- 统计功效更高

**实证发现——来自文献的关键教训：**

| 研究 | 检验策略数 | 核心发现 |
|------|-----------|---------|
| Sullivan, Timmermann & White (1999) | 7,846 条技术交易规则 | 经 RC 校正后，DJIA 上几乎没有规则保持显著 |
| Hsu & Kuan (2005) | 39,832 个模型 | NASDAQ 和 Russell 2000（"年轻"市场）上部分规则显著，但 DJIA 和 S&P 500（"成熟"市场）上不显著 |
| Neuhierl & Schlusche (2011) | 全面的市场择时规则 | 单独看显著的规则，经 RC/SPA 校正后相对 buy-and-hold 失去显著性 |

**核心教训：** 孤立看"盈利"的技术交易规则，一旦施加数据窥探校正，绝大多数失去统计显著性——尤其在成熟市场中。**每次你换一个 cutoff_date 重新跑回测，就是在对同一数据做一次新的"试验"。**

→ **建议：** 在策略评估报告中，必须记录"数据被检视过的总次数"（total number of backtests），并与 Deflated Sharpe Ratio 一同报告。

### 3.3 非因果滤波器在金融时序中的争议

#### 3.3.1 "不存在非因果 DGP"立场

计量经济学界的一个强硬立场：

> 金融和经济学中不存在非因果的数据生成过程（DGP）。资产价格是信息——截至当前——被纳入价格的过程。不存在"未来信息"。（Fama, 1970 及其后续发展）

核心论点：
- 布朗运动/随机游走在本质上是因果的（马尔可夫过程、鞅）
- **观测等价性：** 对每个非因果 AR(1) 模型（特征根在单位圆外），存在统计上完全不可区分的因果 AR(1) 模型
- 非因果模型蕴含对未来信息的依赖，与有效市场假说矛盾

#### 3.3.2 混合因果-非因果（MAR/mVAR）视角

Gourieroux, Jasiak, Lanne, Saikkonen, Fries & Zakoian 等学者认为混合因果-非因果模型在以下场景有用：

- 建模**泡沫**和局部爆炸性形态
- 捕捉**非线性动态**（尖峰、非对称周期）
- 表示理性预期模型（agents 向前看）
- 这些模型假定**非高斯误差**来实现因果与非因果成分的可识别性

**但是**：这些是**模型本身的设定**，不是在已有回测系统上简单叠加一个 `filtfilt`。它们是两种完全不同的方法论。

#### 3.3.3 因果 vs 非因果滤波对比

| 维度 | 因果滤波 | 非因果滤波（`filtfilt`） |
|------|---------|------------------------|
| 使用的信息 | 仅过去和现在 | 过去、现在和**未来** |
| 相位失真 | 有（延迟） | 无（零相位） |
| 重绘（Repainting） | 不重绘 | **重绘**——未来数据影响过去的输出 |
| 前信号伪影 | 无 | 有（向前涂抹） |
| 实时可用 | 是 | 否 |
| 平滑度 | 较低 | 较高（滤波两次） |
| 适用场景 | 实时交易、信号生成 | 离线分析、模式识别（仅限非交易模拟） |

**从 TradingView 社区的实践警告：** "永远不要购买/租用声称无滞后的滤波器——它们要么在重绘，要么是过拟合的。"

→ **建议：** 回测系统中禁止使用任何非因果滤波器。若必须用于离线可视化，明确标注该输出不可用于交易模拟。

### 3.5 形式化解决方案

| 方案 | 解决的问题 | 核心思想 | 复杂度 |
|------|-----------|---------|--------|
| **Purged K-Fold CV** | 时序交叉验证中的信息泄露 | 清除训练集中与测试集标签窗口重叠的观测；加 Embargo 缓冲期 | 中 |
| **Walk-Forward Analysis** | 样本外测试的代表性 | 反复在历史段训练，在紧接的样本外测试，滚动前进 | 中 |
| **Deflated Sharpe Ratio (DSR)** | 多次试验后的选择偏差 | 用试验次数、样本长度、收益分布非正态性调整观测 Sharpe | 中 |
| **Probability of Backtest Overfitting (PBO)** | 最佳回测结果是否为过拟合 | 通过 CSCV 估计最优策略排名由噪声驱动的概率 | 中高 |
| **Combinatorial Purged CV (CPCV)** | 单路径回测的方差问题 | 通过组合训练/测试划分生成多条回测路径，产生性能分布 | 高 |
| **Ghost Data Test** | 检测前视偏差的实操方法 | 插入人造价格尖峰；若尖峰之前信号改变 = 前视偏差 | 低 |

## 4. 工业视角：主流平台的架构选择

### 4.1 QuantConnect/LEAN：事件驱动 + Time Frontier 机制

LEAN 引擎的核心设计哲学：**回测和实盘运行同一代码路径，零改动切换。**

**数据流：**
- 每个数据点携带 `EndTime` 属性
- Bar 数据在**下一周期开始时**才发出（如周五的日线在周六午夜到达）
- Tick 数据即时发出（Time == EndTime）
- `self.Time` 始终等于 Time Frontier
- **超出 Frontier 的数据不可访问**——架构级别的防前视

**每个时间片的执行序列：**
1. 更新算法时间为 Time Frontier
2. 更新 CurrentSlice
3. 触发各类事件回调
4. 更新 Security 对象为最新数据
5. 处理订单撮合、保证金、结算
6. 触发 `OnSecuritiesChanged`
7. 应用分红和拆股
8. 更新 Consolidators
9. 传递 Slice 到 `OnData`
10. 执行组合构建流水线：Alpha → 组合构建 → 风险管理 → 执行

**关键洞察：** LEAN 不"批量计算"——它在每个时间点逐步释放数据，算法永远只能看到"当前之前"的信息。

### 4.2 Backtrader.py：混合向量化预加载 + 顺序执行

Backtrader 的独特之处在于 **preload（预加载）+ runonce（向量化计算指标）+ 顺序执行 `next()` 循环** 的混合模式。

**关键机制：**
- `preload=True`：所有数据预先加载，指标可在向量化模式下一次性计算
- `runonce=True`：指标向量化计算完成后，event-driven 的 `next()` 循环顺序执行
- **Bar 交付规则：** Bars 在交付时已经是 closed（完整柱）
- **x+1 执行：** `next()` 中发出的订单在 bar `x + 1` 执行，绝不在 bar `x`
- **数据同步：** 每个 Feed 独立跟踪自己的下一个可用 datetime；没有新数据的 Feed 提供旧数据点

**前视风险：** `preload=True` 模式下，负索引（`[-1]`）默认可以访问未来数据。这要求开发者有纪律——Backtrader 提供了能力但未强制执行。

**Replay 机制（独有亮点）：** 将小时间框架的每个 tick/分钟 bar 逐个交付给策略，模拟实时数据逐步到达。不同于重采样（直接给聚合结果）。

### 4.3 Zipline Pipeline API：Point-in-Time 双列时间戳门控

Zipline 的 Pipeline API 提供了调研平台中**最精细的 PIT 架构**。

**双列时间戳系统：**

| 列 | 必须 | 含义 |
|----|------|------|
| `asof_date` | 是 | 数据点的有效/观测日期 |
| `timestamp` | 否（回退到 `asof_date`） | 数据**变得可用**的日期 |

**这是防前视的核心机制：** 一个 `asof_date=2014-01-06, timestamp=2014-01-07` 的数据点，在 2014-01-06 的模拟中完全不可见。

**Delta 系统（修正/重述处理）：** 如果 1 月 6 日的值被修正但修正信息在 1 月 9 日才获知，Pipeline 只在 1 月 9 日及之后才应用该修正——完全模拟真实交易者的信息获取时序。

**执行模式：** Pipeline 在 `before_trading_start()` 中运行，仅使用截至前一日收盘的数据。`CustomFactor.compute()` 的多日回溯窗口只能向后看。

### 4.4 VectorBT：全向量化 + 手动 shift 防前视

VectorBT 的根本原则：**每个策略配置 =

每一列是一个独立的策略实例。时间是行，策略变体是列，资产是 MultiIndex 的层级。

**三阶段执行管线：**
```
Indicators → Signals → Portfolio
```

**内置的前视防护：几乎为零。** VectorBT 没有任何显式的时间 Frontier 或 PIT 系统。唯一的防护是开发者惯例：**信号必须 `.shift(1)`**，因为只能在下一根 bar 行动。

**局限性明确：**
- 状态依赖策略（Kelly 仓位管理、加仓、回撤熔断、跨资产协调）需要 workarounds
- 无日内建模
- 反馈循环（仓位管理依赖已实现盈亏 → 已实现盈亏依赖之前变动的仓位）无法向量化

**使用建议：** VectorBT 适合因子快速筛选和参数探索，不适合最终的策略验证。

### 4.5 vnpy：逐K线迭代 + 信号-执行分离

vnpy 按策略类型使用**专用回测引擎**，而非统一引擎：

| 引擎 | 模块 | 用途 |
|------|------|------|
| CTA | `vnpy_ctastrategy.backtesting` | 单品种趋势跟踪 |
| 组合 | `vnpy_portfoliostrategy.backtesting` | 多资产组合 |
| 价差 | `vnpy_spreadtrading.backtesting` | 套利策略 |

**信号时序约定：**

| 阶段 | 时序 | 描述 |
|------|------|------|
| 信号检测 | 当前 bar 收盘 | 使用当前 bar 的 OHLC 计算指标 |
| 交易执行 | **下一 bar 开盘** | 当前 bar 触发的订单在下一 bar 开盘价成交 |

**订单撮合规则：**
- 限价买单：`bar.low_price <= limit_price` → 成交价 = `limit_price + slippage`
- 限价卖单：`bar.high_price >= limit_price` → 成交价 = `limit_price - slippage`
- Stop 买卖单同理，使用 bar 的高低点判断触发

**关键组件：** `BarGenerator`（合成 K 线）、`ArrayManager`（管理历史 K 线数组，提供 SMA/RSI 等指标计算）

### 4.6 架构对比矩阵

| 维度 | LEAN | Backtrader | Zipline | VectorBT | vnpy |
|------|------|------------|---------|----------|------|
| **范式** | 事件驱动流式 | 混合（向量化预加载+事件循环） | Pipeline 快照+事件驱动 | 全向量化 | 迭代事件驱动 |
| **防前视机制** | Time Frontier | closed-bar 交付 + x+1 执行 | 双列时间戳门控 | 手动 `.shift(1)` | bar 收盘信号 + 下一 bar 开盘执行 |
| **PIT 数据** | 间接（EndTime） | 无原生支持 | **原生双列时间戳** | 无 | 无 |
| **日内建模** | Tick/秒级 | Replay 模式 | 无 | 无 | 通过 BarGenerator |
| **信号-执行分离** | 架构强制 | 约定（x+1） | Pipeline 强制（`before_trading_start`） | 手动 `.shift(1)` | 强制（当前 bar 信号→下一 bar 执行） |
| **回测=实盘** | 是（同一代码路径） | 近似 | 否 | 否 | 是（回调系统镜像实盘） |
| **速度** | 较慢 | 中等 | 较慢 | **极快**（毫秒级 10K+ 配置） | 较慢 |
| **状态依赖策略** | 原生支持 | 原生支持 | 受限 | **困难** | 原生支持 |
| **防前视可靠性** | 高（架构级） | 中（依赖开发者纪律） | 高（Pipeline 强制） | 低（全靠开发者） | 中高（约定+引擎检查） |
| **适用场景** | 生产级策略 | 灵活研究+Replay | 因子研究 | 超参优化/快速探索 | 中国期货/股票 CTA |

### 4.7 关键洞察：各平台都在"已知时间点"冻结信号状态

尽管架构迥异，所有五大平台共享一个核心设计原则：

> **在任何"已知时间点"，信号的完整状态必须被冻结且不可变。** 新增数据只能**追加**到未来，不能**改写**历史。

| 平台 | "冻结"实现方式 |
|------|--------------|
| LEAN | Time Frontier — 数据严格按 EndTime 释放；时间之前的数据不可变 |
| Backtrader | Closed-bar 交付 — Bar 交付后内容不再变化；新 bar 是追加 |
| Zipline | Pipeline 在 `before_trading_start` 一次性计算并快照；当日不再重算 |
| VectorBT | 全量预计算后不可变（但未强制因果性检查） |
| vnpy | `on_bar(bar)` 回调式 — bar 交付后即历史；新 bar 是追加 |

**我们的 "Snapshot 模式" 提案正是遵循这一原则。**

## 5. 实用技术目录

### 5.1 因果滤波器选择

| 方法 | 描述 | 用于回测安全？ |
|------|------|--------------|
| Rolling Savitzky-Golay | 仅对过去窗口做多项式拟合，取最后一点 | **安全** |
| 因果傅里叶重构 | 在滚动窗口上 DFT，仅返回最后一点 | **安全** |
| 因果小波重构 | 在滚动窗口上 DWT，仅返回最后一点 | **安全** |
| 单向 Kalman Filter | 仅使用过去观测值 | **安全** |
| 前向 IIR（`lfilter`） | 标准因果数字滤波 | **安全** |
| `filtfilt`（前向-反向） | 两个方向 | **不安全 — 结果无效** |
| centered `savgol_filter` | 窗口中心对称 | **不安全 — 使用未来数据** |
| TradingView `security()` with `lookahead_on` | 从高时间框架拉取未来数据 | **不安全** |

**关于相位滞后的现实接受：** 所有因果滤波器都会引入相位延迟。N 阶低通滤波器的延迟约为 `(N-1)/2` 个样本。这意味着你的信号会滞后于原始价格——这是**真实的**。在实盘交易中，你不可能在数据产生之前就做出反应。

→ **建议：** 将所有 `sosfiltfilt` 替换为 `lfilter`（前向 IIR）；将所有 `savgol_filter` 替换为仅使用过去窗口的滚动实现。接受并记录引入的滞后量，而不是通过非因果滤波掩盖它。

### 5.2 窗口策略：Expanding vs Rolling 的稳定性对比

| 属性 | Expanding Window（扩张窗口） | Rolling Window（滚动窗口） |
|------|---------------------------|-------------------------|
| 训练集大小 | 随时间增长 | 固定为 W |
| 旧数据 | 始终保留 | W 步后丢弃 |
| 参数稳定性 | **更高**（收敛到全样本值） | 较低（随窗口内容变化） |
| 误差估计方差 | 较低 | 较高 |
| 对制度转换的适应性 | 不适用（旧制度持续存在） | 适用 |
| 计算成本 | 后期折叠最高 | 恒定 |
| 适用于 | 平稳过程、短序列 | 非平稳、制度转换 |

**量化证据（GARCH-MIDAS 回测研究）：**
- Expanding window 对大多数模型规格产生了**更低的预测误差**
- Expanding 对 GJR-GARCH 在所有预测区间上都优于 Rolling

**策略回测对比：**

| 指标 | Rolling | Expanding |
|------|---------|-----------|
| 平均回撤 | -19% | **-17%** |
| 平均回撤长度 | 11.4 个月 | **8.1 个月** |
| 年交易次数 | 0.77 | **0.53** |

Expanding window 产生了更浅且更短的回撤——直接的稳定性收益。

→ **建议：** 以 Expanding Window 为默认选项。只有在检测到明显的制度转换后，才切换到 Rolling Window。

### 5.3 Walk-Forward 分析（WFA）

**基本流程：**
1. 在 IS（样本内）窗口上拟合/优化
2. 在紧接的 OOS（样本外）期上测试
3. 向前滚动，重复
4. 将所有 OOS 结果拼接为单一性能序列

**Anchored（锚定）vs Unanchored（非锚定）：**

| 分段 | Anchored IS | Unanchored IS | OOS |
|------|------------|--------------|-----|
| 1 | 1–70 | 1–70 | 71–100 |
| 2 | 1–100 | 31–100 | 101–130 |
| 3 | 1–130 | 61–130 | 131–160 |
| 4 | 1–160 | 91–160 | 161–190 |

- **Unanchored（Rolling）：** IS 起点随步移动。适应制度转换，丢弃过期数据。**短线策略的优选。**
- **Anchored（Expanding）：** IS 起点固定。使用全部历史。**长线/宏观策略更稳定。** 注意：最大回撤等指标随窗口增长而自然增加。

**稳定性评估指标：**

| 指标 | 定义 | 通过阈值 |
|------|------|---------|
| Walk-Forward Efficiency (WFE) | 年化 OOS 收益 / 年化 IS 收益 | > 50-70% |
| IS/OOS Sharpe 比 | IS 与 OOS Sharpe 之比 | < 2.0；OOS >= IS 的 50% |
| 盈利运行比例 | OOS 期盈利的百分比 | > 70% |
| 参数不稳定性 | 最优参数在各窗口间的方差 | 低 = 鲁棒 |
| Calmar Ratio (OOS) | 年化收益 / 最大回撤（OOS） | > 1.0 |

**红旗警告：**
- Anchored vs Unanchored 结果显著偏离 → 制度依赖，不鲁棒
- 最优参数附近出现陡峭峰值 → 过拟合。平坦高原 → 鲁棒
- 单个 OOS 段贡献 > 30-50% 总利润 → 脆弱

→ **建议：** 使用 30+ 个 OOS 段达到统计显著性。同时比较 Anchored 和 Unanchored。用 CPCV 做更深层验证。

### 5.4 Point-in-Time 数据架构

**定义：** PIT 数据不仅记录一个数据值，还记录**该值何时变得可用于决策**。它区分**价值日期**（数据代表什么时间的现实）和**可用日期**（该信息何时被知晓）。

**时间差异的三个关键来源：**
1. **发布延迟** — 季度财报在季度结束后 4-6 周才报告
2. **修正和重述** — 历史会被改写（如 2008-2009 年美国失业数据从最初估计的 480 万修正到 870 万）
3. **幸存偏差** — 指数成分股列表被重写（Lehman Brothers、Enron 从当前成分股中消失）

**Microsoft Qlib 的开源 PIT 实现：**
- 每个特征两个文件：`XXX_a.data`（二进制数组）+ `XXX_a.index`
- 每行：`date`（发布日期）、`period`（报告期）、`value`（指标值）、`_next`（下一版修订的字节偏移量）
- 修订通过追加新行处理（同 `period`、更晚 `date`）；`_next` 链接修订链表
- 在任何历史截止点的查询沿链表返回截至那一刻的最新版

**行业趋势：** 向**仅追加、不可变、带时间戳修订的数据存储**方向发展：
- 基于 Snowflake 的交付（Glassnode, FactSet）
- S3-compatible 扁平文件 + 版本元数据（FinFeedAPI）
- 零拷贝架构避免 ETL 复制（CloudQuant）

→ **建议：** 长期目标是将数据存储迁移至仅追加+时间戳模型。中期可在现有数据上叠加简单的 PIT 包装层。

### 5.5 Snapshot/Precompute 模式

**模式描述：** 将计算昂贵的信号/预测管线与回测引擎分离。先用严格因果的方式在完整数据上预计算信号，保存为冻结快照，然后以自定义数据集形式流入回测。

**QuantConnect 的实现：**
1. 在 Research 环境中：收集历史价格，用仅过去数据做特征工程，训练模型，将每日预测导出为 JSON 到 Object Store
2. 自定义 Universe：`PythonData` 子类从 Object Store 读取 JSON
3. 算法：订阅自定义 Universe；定时事件根据预计算预测做组合再平衡

**收益：**

| 收益 | 说明 |
|------|------|
| **速度** | 回测完全跳过特征计算和模型推理 |
| **迭代速度** | 可以测试不同阈值、再平衡规则或风险覆盖层而不重跑 ML 管线 |
| **可复现性** | 预测被冻结——回测运行之间无漂移 |
| **现实性** | PIT 引擎在预计算阶段强制使用仅过去数据的纪律 |

**注意事项（关键）：** 这是一个两阶段方案。信号预计算阶段本身必须严格因果。预计算步骤中的任何前视偏差都会被**永久固化**到快照中。

→ **这是我们的 "Snapshot 模式" 方案的直接行业参照。**

### 5.6 K线合成与部分周期处理

**核心问题：** 当前（正在形成中的）K 线的时间上是不完整的——其 OHLCV 随每个 tick 变化。在回测中使用未确认的 bar 数据产生两个问题：
1. **前视偏差**（如果你在 bar 完全形成前就按其最终收盘价行动）
2. **信号重绘**（如果新 tick 到来时指标重算，历史信号移位）

**各平台处理方式：**

| 平台 | 部分 Bar 策略 |
|------|-------------|
| **NautilusTrader** | `BarAggregator` with `set_partial()`, `skip_first_non_full_bar`, `await_partial`——一流原生支持 |
| **MetaTrader 4/5** | Bar 0 被识别为未完成；`Every tick` 模式建模 bar 内动作；`Open prices only` 完全规避 |
| **MultiCharts** | IOG（Intrabar Order Generation）启用部分 bar 交易 |
| **NinjaTrader** | `Calculate.OnBarClose` vs `OnEachTick` vs `OnPriceChange` 控制指标更新时机 |
| **Pine Script** | `barstate.isconfirmed` 门控——仅在完全闭合的 bar 上执行信号逻辑 |

**多时间框架的挑战：** 在 5 分钟 bar 上回测同时引用 1 小时 bar。理想的解决方案是使用仅反映截至当前低时间框架 bar 收盘时数据的部分完成的高时间框架 bar。

**最佳实践：**
1. 信号生成**始终使用 bar 收盘数据**（`barstate.isconfirmed`、`OnBarClose`）
2. 引用高时间框架时：`source[barstate.isconfirmed ? 0 : 1]`——当高 TF bar 仍开放时使用前一根已确认 bar 的值
3. **执行移位到下一 bar 开盘：** 绝不在信号出现的同一 bar 上执行
4. 初始化期间使用 `skip_first_non_full_bar` 避免初始部分 bar 伪影

→ **建议：** 在我们的系统中强制实施 Bar-Close 门控——信号计算仅在完全闭合的 K 线上进行。

### 5.7 信号跳跃预防技术

#### 5.7a 滞回/死区滤波（Hysteresis/Deadband）

一个"防抖"基线，忽略小波动，仅在价格有意义地偏离时才反应：

- **外带（Enter Band）：** 较宽——价格必须穿越才能触发状态变化
- **内带（Exit Band）：** 较窄——价格必须穿越才能回退
- 创造一个"持有区"防止快速翻转

**参考参数（来自 BackQuant 实现）：**

| 用例 | 模式 | 关键参数 |
|------|------|---------|
| 通用 | ATR (14) | Enter Mult=1.0, Exit Mult=0.5, Response=0.20 |
| 震荡区间 | ATR (14) | ATR Mult=2.0, Response=0.15 |
| 快速日内 | 百分比 (0.1-0.3%) | Enter=1.0, Exit=0.4-0.6, Response=0.30-0.40 |
| 期货 Tick | Ticks | Enter=1.0, Exit=0.5, Response=0.25 |

#### 5.7b 确认 K 线 / 延迟入场

来自 Pine Script 生态系统的技术：
1. **`barstate.isconfirmed` 门控：** 仅在完全闭合 bar 上执行
2. **仅历史限制：** `if not barstate.isrealtime` 限制仅历史 bar 执行
3. **两根 bar 确认：** 信号需在连续两根确认 bar 上保持才能行动。增加延迟，大幅削减虚假信号
4. **移位执行：** `df['signal'].shift(1)`——始终在下一 bar 开盘行动

#### 5.7c Kalman 滤波平滑

Kalman 滤波器是一种递归贝叶斯估计器，从噪声价格数据中提取潜在"真实"趋势：
- Predict → Measure → Update 循环
- 通过 Kalman Gain 融合新观测与先验估计

**量化收益（2025 年 DRL + Kalman 研究）：**

| 指标 | 改善幅度 |
|------|---------|
| 收益 | +244% 到 +822% |
| Sharpe 比 | 16x 到 29x |
| 回撤降低 | 88% 到 96% |
| 最大回撤 | 0.48% 到 1.39% |

**关键权衡：** Kalman 超参数（过程噪声 Q、观测噪声 R）高度敏感——小变化显著影响性能。简单策略（如均线交叉）在参数误设时可能比 Kalman 优化策略**更鲁棒**。

→ **建议：** 将 Kalman 滤波与制度检测（HMM、Markov switching）结合使用以提高稳定性。

#### 5.7d 多时间框架共振

要求多个时间框架一致才生成信号。例如：M15、H1、H4 中至少 2/3 一致。结合状态机（牛市/熊市/中性）防止冲突信号。

#### 5.7e CPCV（组合清除交叉验证）

Lopez de Prado（2018, Chapter 12）：

- 将时间序列划分为 N 个连续组
- 通过组合训练/测试划分生成多条回测路径
- **清除：** 训练集中标签窗口与测试集重叠的观测
- **禁运：** 在每个测试集之后增加额外缓冲
- 结果：性能指标的**分布**（而非单一路径），使信号稳定性评估变得诚实

**信号稳定性关注：** 非连续训练期可能在接缝处产生人工不连续性
**信号稳定性收益：** 通过多条路径平均降低方差，假发现率低于单路径 WFA

→ **建议：** 在 Walk-Forward 验证框架中内置 CPCV 选项。

### 5.8 幽灵数据测试（Ghost Data Test）

**步骤：**
1. 在历史数据序列中间位置插入一个人造价格尖峰（如 +5 标准差）
2. 重新运行整个信号计算管线
3. 检查尖峰**之前**的信号值是否发生变化
4. 如果变化 → 存在前视偏差

这是检测前视偏差最简单、最有效的**冒烟测试**。

### 稳定性技术决策矩阵

| 问题 | 技术 | 复杂度 | 影响级别 |
|------|------|--------|---------|
| 滤波器导致的前视偏差 | 因果滤波器；单向滚动窗口 | 低 | **关键** |
| 数据导致的前视偏差 | PIT 数据架构 | 高（基础设施） | **关键** |
| 信号重绘 | Bar-close 确认；shift-1 执行 | 低 | 高 |
| 信号震荡 | 滞回/死区；确认 K 线 | 低 | 高 |
| 参数不稳定 | Expanding Window；WFA 参数追踪 | 中 | 高 |
| 单路径过拟合 | CPCV；Anchored vs Unanchored 对比 | 中高 | 高 |
| 多 TF 泄露 | 高 TF 引用的三元门控 | 低中 | 高 |
| ML 推理瓶颈 | Snapshot/Precompute 模式 | 中 | 中（速度） |
| 信号噪声 | Kalman 滤波平滑 | 中高 | 中高 |
| 模型评估方差 | Expanding Window；CPCV 多路径 | 中 | 中 |

## 6. 与我们的项目的对照分析

### 6.1 我们的问题在行业坐标系中的位置

我们的信号不稳定性问题可以精确地定位在行业共识框架中：

| 坐标轴 | 我们的位置 |
|--------|-----------|
| **偏误类型** | 前视偏差（Look-Ahead Bias），由非因果滤波直接导致 |
| **表现症状** | 信号重绘（Repainting）——历史 BS 点随 cutoff_date 变化而漂移 |
| **根因** | `sosfiltfilt`（前向-反向滤波）+ centered `savgol_filter` + 滑动窗口机制的三重组合 |
| **影响量级** | 6 级级联放大——从滤波器的边界扭曲到策略评估的全局不可靠 |
| **行业严重性评级** | **严重**——与 TradingView "不要购买零滞后滤波器"警告处于同一等级 |

**在"量化七大罪"中的映射（Luo et al., Deutsche Bank, 2014）：**

| 罪 | 我们的状况 |
|----|-----------|
| #1 幸存偏差 | 如果数据源未做退市处理，存在风险 |
| **#2 前视偏差** | **直接命中——当前面临的核心问题** |
| #3 叙事偏差 | 事后解释信号形态是易犯错误 |
| **#4 数据窥探** | **间接命中——每次换 cutoff_date 重跑 = 重复试验** |
| #5 交易成本忽略 | 取决于当前回测实现 |
| #6 异常值 | 取决于策略设计 |
| #7 非对称做空成本 | 取决于策略类型 |

### 6.2 Snapshot 模式 ≈ Zipline Pipeline API + QuantConnect Precompute

我们提出的 "Snapshot 模式" 在行业中有两个精确的对标：

| 我们的方案 | 行业对标 | 相似度 |
|-----------|---------|--------|
| 预计算信号并冻结为快照 | **Zipline Pipeline API**（`before_trading_start` 一次性计算，当日不再重算） | **概念等价** |
| 将快照作为自定义数据源供回测引擎消费 | **QuantConnect Precomputed ML Predictions**（Research 环境预计算 → Object Store → 自定义 Universe 订阅） | **架构等价** |
| 快照计算阶段的严格因果约束 | **所有平台的共同原则**（Time Frontier / Pipeline / closed-bar / shift-1） | **概念等价** |

**这意味着：我们的方案不是"草根创新"，而是行业成熟模式在我们技术栈上的适配实现。**

### 6.3 Quick Wins 与行业实践的对应

我们之前识别的 Quick Wins 在行业实践中都有直接先例：

| Quick Win | 行业先例 |
|-----------|---------|
| `sosfiltfilt` → `lfilter` | 因果滤波的行业标准做法；TradingView 社区的"零滞后 = 重绘"警告 |
| centered `savgol_filter` → 前向滚动窗口 | 与 NinjaTrader `OnBarClose`、Pine Script `barstate.isconfirmed` 同源思想 |
| Bar-Close 门控 | 几乎所有平台的共同约定（LEAN 的 EndTime、Backtrader 的 closed-bar、vnpy 的 bar 收盘信号） |
| Ghost Data Test 加入 CI | 学术界 + 工业界公认的前视偏差检测方法 |

### 6.4 我们的项目还缺什么

与行业标准对比，我们的系统存在以下缺口：

| 缺失项 | 重要性 | 行业谁有 | 缺失影响 |
|--------|--------|---------|---------|
| **PIT 数据架构** | 高 | Zipline、Qlib、StarQube、FactSet、LSEG | 基本面数据的前视偏差无法根除 |
| **Walk-Forward 验证框架** | 高 | NinjaTrader、MultiCharts、所有专业平台 | 无法评估策略在样本外的真实表现 |
| **Ghost Data Test** | 高 | 学术界 + 工业界最佳实践 | 前视偏差无自动化检测 |
| **DSR/PBO 报告** | 中 | Lopez de Prado 方法论 | 无法量化过拟合风险 |
| **CPCV 多路径验证** | 中 | Lopez de Prado (2018) | 单一路径回测的方差无法评估 |
| **多时间框架门控** | 中 | Pine Script、NautilusTrader | 多 TF 策略存在跨 TF 信息泄露 |
| **信号滞回/死区** | 低中 | BackQuant、Pine Script 社区 | 信号震荡/翻转 |
| **正式化因果约束检查** | 低中 | QuantConnect Time Frontier 是架构级 | 依赖开发者纪律而非系统强制 |

## 7. 建议路线图

### 7.1 短期（1-2 周）：Quick Wins + 检测

**目标：消除已知的非因果滤波源头 + 建立自动化检测能力**

```
Phase 1.1: 滤波器替换
├── sosfiltfilt → lfilter（前向 IIR）
├── centered savgol_filter → 仅使用过去窗口的滚动实现
├── 所有滤波位置添加因果性注释
└── 验证：Ghost Data Test 通过

Phase 1.2: Bar-Close 门控
├── 信号计算仅在完全闭合 K 线上执行
├── 添加 barstate.isconfirmed 等价检查
└── 验证：部分 bar 场景下 BS 点不变

Phase 1.3: Ghost Data Test 集成
├── 实现人造尖峰注入工具
├── 加入 CI 流水线作为冒烟检测
└── 验证：CI 自动检测前视偏差
```

**验收标准：** Ghost Data Test 在 CI 中自动通过；同一历史时期的 BS 点在 cutoff_date 变化时不再漂移。

### 7.2 中期（1-2 月）：Snapshot 模式 + Walk-Forward

**目标：实施信号预计算-冻结-消费架构 + 建立样本外验证能力**

```
Phase 2.1: Snapshot 模式核心
├── 设计 Snapshot 数据格式（信号值 + 时间戳 + 版本号）
├── 实现 Snapshot 预计算管线（严格因果）
├── 回测引擎改为消费 Snapshot 而非实时计算
└── 验证：多次运行产生完全一致的 BS 点

Phase 2.2: Walk-Forward 验证框架
├── 实现 Anchored + Unanchored WFA
├── 生成 WFE、IS/OOS Sharpe 比、参数稳定性图
├── 至少 30 个 OOS 段
└── 验证：WFE > 50% 且参数稳定

Phase 2.3: 信号稳定性仪表板
├── BS 点一致性度量（不同 cutoff_date 下的 Jaccard 指数）
├── 参数稳定性可视化
├── OOS 性能时间序列
└── 验证：单个界面覆盖所有稳定性指标
```

**验收标准：** 任意 cutoff_date 下同一历史期的 BS 点完全一致；Walk-Forward 报告自动生成。

### 7.3 长期（3-6 月）：PIT 数据架构 + CPCV

**目标：根除所有前视偏差来源 + 建立行业标准的验证方法**

```
Phase 3.1: PIT 数据架构
├── 数据存储迁移至仅追加 + 时间戳模型
├── 实现 asof_date / timestamp 双列系统
├── 基本面数据的 PIT 处理
└── 验证：使用 PIT 数据 vs 非 PIT 数据的性能差异报告

Phase 3.2: Purged K-Fold / CPCV
├── 实现 Purged K-Fold CV（Lopez de Prado 2018, Ch12）
├── 实现 CPCV 多路径生成
├── 生成 PBO（回测过拟合概率）报告
└── 验证：PBO < 0.3 且跨路径性能分布合理

Phase 3.3: DSR（Deflated Sharpe Ratio）报告
├── 实现 DSR 计算
├── 在所有回测报告中自动包含 DSR
├── 记录"试验总次数"并随 Sharpe 报告
└── 验证：DSR 高于基准
```

**验收标准：** 基本面策略回测中前视偏差为零；CPCV 多路径性能分布收窄；DSR 自动随回测报告生成。

### 7.4 技术债务识别与优先修复顺序

| 优先级 | 技术债务 | 修复方案 | 预计工作量 |
|--------|---------|---------|-----------|
| **P0** | 非因果滤波器在回测中使用 | 替换为因果实现 | 1-3 天 |
| **P0** | 无前视偏差自动化检测 | Ghost Data Test 入 CI | 1-2 天 |
| **P1** | 无 Bar-Close 门控 | 实现 bar 状态检查 | 1-2 天 |
| **P1** | 信号实时计算 → 不可重复 | Snapshot 模式 | 1-2 周 |
| **P2** | 无 Walk-Forward 验证 | WFA 框架 | 1-2 周 |
| **P2** | 数据无 PIT 标记 | PIT 包装层或迁移 | 2-4 周 |
| **P3** | 无过拟合量化指标 | DSR/PBO 报告 | 1 周 |
| **P3** | 单路径回测 | CPCV 多路径 | 1 周 |
